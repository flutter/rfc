# RFC 510.0000: Targeting Custom Embedders with Flutter Tools

## Summary

This RFC proposes a first-class, isolate-based platform extension architecture for the Flutter CLI (`flutter_tools`). By decoupling target platform tooling from the core Flutter SDK into project-scoped Dart packages (`package:flutter_tools_extension` and `package:flutter_tools_core`) that communicate with the Flutter Tool over a structured JSON-RPC 2.0 protocol, third-party and custom embedder authors can hook their devices, build targets, platform templates, SDK artifacts, and diagnostics directly into standard `flutter` commands (`doctor`, `config`, `create`, `devices`, `emulators`, `run`, `attach`, `logs`, `install`, `screenshot`, `drive`, `test`, `build`, `assemble`, `precache`, and `clean`) without forking the Flutter repository or maintaining bespoke wrapper CLIs.

## Overview

Custom Flutter embeddings (such as webOS, Tizen, automotive head units, and industrial displays) currently lack first-class access to the standard functionality of the `flutter` command-line tool. While the C/C++ Embedder API provides a stable boundary for integrating the Flutter runtime on non-standard operating systems, the developer tooling in `flutter_tools` has historically hard-coded assumptions around its six first-party target platforms (Android, iOS, web, Linux, macOS, and Windows).

Consequently, embedder maintainers have been stuck between two difficult choices:

1. **Maintaining a fork of the Flutter SDK or a bespoke wrapper CLI** (`flutter-elinux`, `flutter-tizen`, `flutter-pi` tooling) that duplicates command routing, argument parsing, and asset bundling while constantly drifting behind upstream SDK releases and breaking standard IDE integrations.
2. **Using `flutter custom-devices`**, which substitutes shell commands for basic device discovery, installation, and port forwarding via a static JSON configuration file, but cannot express custom build pipelines (`flutter build`, `flutter assemble`), platform scaffolding (`flutter create`), SDK artifact management (`flutter precache`), environment diagnostics (`flutter doctor`), or native plugin compilation.

To support custom embedders and target platforms without forks, the Flutter Tool needs to be pluggable, providing embedder maintainers a way to hook into existing commands that require knowledge of the target platform. To achieve this, the Flutter Tool will support project-scoped tool extensions (simply referred to as "extensions" throughout the rest of this document) that run in separate Dart isolates and provide platform-specific implementations for key operations performed by the tool.

### In Scope

Once implemented, the Tool Extension API will allow extensions to provide support for:

* Downloading and caching necessary artifacts for the target platform (e.g., custom embeddings of the Flutter engine or cross-compilation toolchains) via `flutter precache`
* Interacting with custom devices (e.g., detection via `flutter devices`, deployment and hot reload via `flutter run` and `flutter attach`, log streaming via `flutter logs`, standalone installation via `flutter install`, screenshot capture via `flutter screenshot`, and end-to-end testing via `flutter drive` and `flutter test integration_test -d <device>`)
* Selecting out-of-tree target devices and launching, hot reloading, and debugging applications directly from IDEs (VS Code and IntelliJ/Android Studio) via `flutter daemon` without custom IDE plugins
* Listing, launching, and creating device emulators (`--create`) via `flutter emulators`
* Registering high-level `flutter build <target>` subcommands and fine-grained `flutter assemble` build targets to handle compilation and bundling steps specific to the target platform
* Running custom `flutter doctor` checks to verify that the host build environment is set up for the target platform
* Registering custom feature flags and configuration options for use with `flutter config`
* Scaffolding custom platform runner directories for new or existing applications and plugins via `flutter create --extension=<package> <dir>` (or `flutter create . --platforms=<platform>` when the extension is already in `dev_dependencies`)
* Cleaning up extension-specific build outputs during `flutter clean`

See [Appendix: Usage Examples](#appendix-usage-examples) for an end-to-end extension implementation and application developer CLI walkthrough.

### Non-Goals & Out of Scope

* **Security Sandboxing**: This design focuses on process stability and isolating the tool from uncaught Dart exceptions in buggy extensions, not on providing an OS-level security sandbox for executing untrusted code (see [Section 3.3](#33-isolate-isolation-boundaries--process-wide-constraints)). Once dependencies are resolved via `flutter pub get`, extensions run with the same permissions as the Flutter Tool, matching the trust model of Dart build hooks (`package:hooks`) and analyzer plugins.
* **Non-Dart Extensions**: This proposal only supports extensions written in Dart to leverage the isolate-based communication model and shared packages.
* **Universal Dart CLI Extensibility**: While the underlying isolate JSON-RPC runner is generic, the scope of this document is limited to the Flutter Tool and does not aim to provide a general plugin system for all Dart CLI tools.

To keep this RFC focused on the core extension mechanism (`510-tool`), custom embedder support (`450-embedded`), and custom platform plugin interop (`440-plugins`), the following items are explicitly **out of scope for this RFC** and will be proposed in dedicated follow-up RFCs:

1. **Migrating Built-In First-Party Platforms to Extensions**: Any future proposal to extract built-in platform implementations (Android, iOS, web, Linux, macOS, Windows) into bundled extensions affects `410-mobile`, `420-web`, and `430-desktop` and requires a dedicated bundled-extension loading model (independent of project `dev_dependencies`) and separate RFC review.
2. **Deprecating `flutter custom-devices`**: Deprecating the experimental `flutter custom-devices` feature and shipping a compatibility extension package (`flutter_custom_devices` reading existing `custom_devices.json` files) will be proposed in a separate follow-up RFC once the extension ecosystem stabilizes.
3. **IDE "New Project" Wizard Integration**: While post-creation IDE workflows (device discovery, launching, hot reload, debugging, and DevTools) work out of the box through `flutter daemon`, both VS Code (`Dart-Code`) and IntelliJ/Android Studio (`flutter-intellij`) currently hardcode the six built-in platforms in their "New Project" wizard UIs without querying `flutter daemon`. Surfacing custom extension packages and platform options inside IDE "New Project" wizards (invoking `flutter create --extension=<package>` under the hood) will be pursued as follow-up IDE plugin and daemon work.

## Detailed Design

### 1. Package Boundaries & Workspace Layout

The extension framework splits contracts across three packages in the Flutter repository workspace:

```mermaid
flowchart LR
  subgraph Host["Host CLI Process"]
    direction TB
    FT["package:flutter_tools"]
    FTC1["package:flutter_tools_core"]
    FT --> FTC1
  end

  subgraph Iso["Extension Isolate (Isolate.spawnUri)"]
    direction TB
    EXT["3P Extension Package"]
    FTE["package:flutter_tools_extension"]
    FTC2["package:flutter_tools_core"]
    EXT --> FTE
    FTE --> FTC2
  end

  Host <-->|"JSON-RPC 2.0 over IsolateChannel"| Iso
```

1. **`package:flutter_tools_core`** (`packages/flutter_tools/packages/flutter_tools_core/`):
   * **Shared by both the Flutter Tool and extensions**: Contains pure, immutable wire models, enums, and internal JSON-RPC method/parameter wire constants for devices and emulators, build and assemble targets, doctor diagnostics, configuration flags, templates, SDK artifacts, and capability handshake metadata. Imported directly by core non-extension `package:flutter_tools` subsystems (such as `HostPlatform` in `os.dart`, `CpuArch` in `build_info.dart`, and `ValidationResult` in `doctor_validator.dart`) without pulling isolate or JSON-RPC runtime dependencies into core tool models.
   * Depends only on `package:collection` and `package:meta` (with zero `dart:io`, `dart:isolate`, or `dart:ffi` imports) so it can be published to `pub.dev` without pulling internal `flutter_tools` implementation details into third-party packages.
2. **`package:flutter_tools_extension`** (`packages/flutter_tools/packages/flutter_tools_extension/`):
   * **Extension-author SDK**: Re-exports `package:flutter_tools_core` (so extension authors declare only `package:flutter_tools_extension` in their `pubspec.yaml`) and provides `package:flutter_tools_extension/flutter_tools_extension.dart` (`ToolExtensionEntryPoint` isolate runner and `*Service`, `BuildTarget`, and `AssembleTarget` `abstract base class` interfaces) along with extension testing utilities in `package:flutter_tools_extension/testing.dart` (`ServiceTestHarness` and `verifyExtensionPackage`, kept free of `package:test_api` to avoid version-solve conflicts with `flutter_test`).
3. **`package:flutter_tools`** (`packages/flutter_tools/`):
   * **For the host CLI only (never imported by extensions)**: Implements host-side extension discovery, kernel snapshot compilation and caching, isolate connection management, and adapters bridging JSON-RPC calls into native Flutter Tool subsystems (doctor, config, templates, devices, build system, artifacts, and clean), depending only on `package:flutter_tools_core` (never importing `package:flutter_tools_extension`) while extensions never import `package:flutter_tools`.

Splitting `package:flutter_tools_core` from `package:flutter_tools_extension` keeps `package:flutter_tools_core` as the pure-Dart, zero-`dart:io` model package shared across built-in `package:flutter_tools` subsystems and third-party extensions without pulling isolate or JSON-RPC dependencies into core tool models, while keeping extensions completely insulated from internal `package:flutter_tools` APIs. To prevent cross-package version skew between the two packages (such as Dart 3 exhaustive `switch` mismatches across minor versions), `package:flutter_tools_extension` re-exports `package:flutter_tools_core` and pins an **exact lockstep version** (`flutter_tools_core: 0.x.y`, never a caret `^0.x.0` range) in its published `pubspec.yaml`.

Both `package:flutter_tools_core` and `package:flutter_tools_extension` remain in-tree under `packages/flutter_tools/packages/` inside `flutter/flutter` (as Pub workspace members) so protocol contracts, `flutter_tools` host adapters, and integration tests evolve atomically in single PRs without cross-repository roll overhead. Releases publish directly from `flutter/flutter` to `pub.dev` via a tag-triggered GitHub Actions OIDC workflow (`flutter_tools_core-v<version>` and `flutter_tools_extension-v<version>`, modeled on `dart-lang/sdk`'s `.github/workflows/publish.yml`) and are resolved by extension packages via standard semantic versioning rather than being pinned to the exact version shipped inside the user's Flutter SDK. Because extensions run in separate isolates and communicate with the Flutter Tool over a backwards-compatible JSON-RPC 2.0 wire protocol (rather than sharing in-memory Dart class hierarchies across isolate boundaries), an extension compiled against an older minor version of `package:flutter_tools_extension` remains compatible with newer Flutter SDKs even when newer SDKs add methods, fields, or parameters to the service interfaces.

### 2. Project-Scoped Discovery & Workspace-Local Kernel Compilation

#### 2.1 Project-Scoped Discovery via `pubspec.yaml`

Following the precedent established by DevTools extensions, extensions are shipped as standard Dart packages and declared in a project's `pubspec.yaml` (typically under `dev_dependencies`). Because `.dart_tool/package_config.json` only maps package names to resolved `rootUri`s across the flat transitive dependency closure without recording direct dependency edges, the Flutter Tool reads direct `dependencies` and `dev_dependencies` from `pubspec.yaml`, resolves only those direct dependencies' package roots in `.dart_tool/package_config.json` (`package:package_config`), and discovers any direct dependency containing `extension/flutter_tools/extension.dart` (verifying after symlink resolution that the entrypoint resides within the package root). This enables teams to lock extension versions in version control and execute reproducible builds across developer machines and CI environments with a standard `flutter pub get`.

To prevent unvetted transitive dependencies from executing code automatically and avoid running host-specific service initialization on unsupported hosts, the tool enforces several safeguards during discovery:

* **Direct Dependency & Pub Workspace Filtering**:
  * **Standalone projects & workspace members**: When invoked inside a standalone project or a Pub workspace (`resolution: workspace`) member package, the tool unions direct `dependencies` and `dev_dependencies` from the active member's `pubspec.yaml` and the Pub workspace root `pubspec.yaml` (if present), isolating sibling workspace packages from unrelated custom `flutter build` or `flutter create` targets.
  * **Pub workspace roots**: When invoked directly at a Pub workspace root (`pubspec.yaml` containing a `workspace:` list), workspace and environment commands (`flutter doctor`, `flutter devices`, `flutter emulators`, `flutter config`, `flutter precache`, `flutter daemon`, and workspace-wide `flutter clean`) union direct `dependencies` and `dev_dependencies` across the workspace root and all `workspace:` member `pubspec.yaml` files against the single shared workspace `.dart_tool/package_config.json`. Project-targeted executions (`flutter run`, `flutter build`, and `flutter daemon` `app.start`) remain gated on the target project's (plus workspace root's) direct dependencies and `isSupportedForProject`.
* **Host Platform & Service Capability Filtering**: Because `dart compile kernel` is platform-independent Dart front-end compilation, the tool compiles an extension snapshot once per cache key and caches its handshake `ToolExtensionCapabilities` (`services` and optional `supportedHostPlatforms`). Extension `main()` entrypoints and `*Service` constructors must be side-effect-free, deferring any host-specific work to service RPC handlers (`getDevices`, `runDiagnostics`, `build`, etc.). When `supportedHostPlatforms` is non-null and excludes the current `HostPlatform`, `ToolExtensionEntryPoint.run` skips `service.initialize()`, completes the `extension.getCapabilities` handshake so the host records the cached capabilities, and shuts down cleanly (logging at trace level only). On subsequent CLI invocations, the tool skips spawning isolates whose cached `services` do not apply to the active command or whose cached `supportedHostPlatforms` excludes the current host.
* **Safe Mode Bypass**: To ensure users can recover from broken or misbehaving extensions, passing `--no-extensions` (`--[no-]extensions`) on the command line or setting `FLUTTER_NO_EXTENSIONS=1` (`true` or `yes`) in the environment skips extension discovery and isolate spawning for the invocation.
* **`pub get` Lifecycle Ordering & `flutter create` Discovery**: Commands that register dynamic CLI flags or subcommands from extensions ensure `.dart_tool/package_config.json` is up to date before querying available extensions, and refresh discovery if `pub get` or `pub add` resolves new packages during command execution. `CreateCommand` scopes extension discovery to `<target_dir>` rather than the caller's working directory and supports `--extension=<package[@descriptor]>` for single-command extension bootstrap (see [Section 4.4](#44-platform-templates--scaffolding-flutter-create)).
* **Long-Lived Session & Multi-Project Invalidation (`flutter daemon`)**: In long-lived sessions such as `flutter daemon`, where the initial working directory may be a multi-root workspace parent and dependencies can change mid-session (`flutter pub add --dev`), the daemon discovers extensions from the initial working directory (including Pub workspace members when started at a workspace root) plus any `projectDirectory` roots registered via `app.start`, refreshes discovery whenever `.dart_tool/package_config.json` changes in any tracked root, and deduplicates discovered extensions across tracked roots by extension package name (if two standalone roots in an IDE multi-root workspace resolve different versions of the same extension package, the first registered root wins for global `device.enable` polling and the tool logs a warning). Launching an application via `app.start` for a `projectDirectory` that does not declare that extension in its own (or its workspace root's) `pubspec.yaml` remains gated by project dependency membership and `isSupportedForProject`.

#### 2.2 Entrypoint Convention & Capability Registration (`extension/flutter_tools/extension.dart`)

Every extension package exposes `extension/flutter_tools/extension.dart` at its package root with the isolate entrypoint signature `Future<void> main(List<String> args, Object? message)`. Placing the entrypoint under `extension/flutter_tools/extension.dart` scopes the extension to `flutter_tools` (matching the `extension/<target_package>/` directory layout used by DevTools extensions) without requiring a separate YAML manifest file, while keeping `bin/` reserved for actual CLI executables (preventing broken `dart run` invocations on `SendPort` scripts and preventing `pub.dev` / `pana` from falsely tagging tool extensions as `has:executable`). While discovery inspects only for `extension/flutter_tools/extension.dart` regardless of package name, extension authors are encouraged to use concise, recognizable `dev_dependencies` package names such as `<platform>_flutter_tools` or `flutter_<platform>_tools` (for example, `tizen_flutter_tools` or `flutter_custom_tools`), kept separate from any runtime Dart package so `dart:io` and `dart:isolate` dependencies stay out of application `dependencies`.

Service and host-platform registration happen in one place only in typed Dart with dartdoc: the `List<ToolExtensionService>` and optional `Set<HostPlatform>? supportedHostPlatforms` passed to `ToolExtensionEntryPoint.run` (see [Section 4.1](#41-core-service-entrypoint--error-abstractions)), while build subcommand names, custom template platforms, and custom CLI flags and options are declared once in Dart on `BuildTarget`, `TemplateService`, and `ConfigService`. `supportedHostPlatforms` defaults to `null` (meaning all host platforms are supported), and passing a non-null empty set (`{}`) throws an `ArgumentError` (and fails `verifyExtensionPackage`) so an extension cannot accidentally disable itself on all hosts. Both `services` and `supportedHostPlatforms` must depend **only on the extension package snapshot** (never branching on environment variables, `PATH` or installed host toolchains, current working directory, or project contents; host environment and project checks belong in `DiagnosticsService`, `DeviceService.getDevices`, and `isSupportedForProject`). After an extension's first handshake (`extension.getCapabilities`; see [Section 3.1](#31-json-rpc-20-transport-handshake--exit-monitoring)), the tool caches its `ToolExtensionCapabilities` (`services` and `supportedHostPlatforms`) alongside the compiled `.dill` snapshot (see [Section 2.3](#23-workspace-local-kernel-dill-compilation-cache)) so subsequent CLI invocations skip spawning isolates whose cached `services` do not apply to the active command or whose cached `supportedHostPlatforms` excludes the current host.

#### 2.3 Workspace-Local Kernel (`.dill`) Compilation Cache

Because `Isolate.spawnUri` requires either a Dart source URI with a resolved package config or a precompiled Dart kernel (`.dill`) snapshot, the Flutter Tool compiles extension entrypoints with `dart compile kernel --depfile` into a workspace-local cache to keep subsequent CLI invocations fast without coupling cache keys to internal Pub lockfile or dependency-graph formats:

* **Location**: `<workspace>/.dart_tool/flutter_tools/extensions/<package_name>/extension.dill` alongside `extension.dill.d` and `extension.dill.stamp`, where `<workspace>` is the Pub workspace root, or the project root for standalone projects (removed by `flutter clean` when run from the workspace root or a standalone project).
* **Invalidation & Compilation-Start Timestamp**: Before reading `.dart_tool/package_config.json` or invoking `dart compile kernel`, the tool records the compilation start timestamp (`compiledAt`, truncated down to whole seconds) for the `extension.dill.stamp` file committed after compilation (containing `compiledAt`, a per-compilation `buildToken`, the exact Dart SDK revision from `bin/cache/dart-sdk/revision`, the raw SHA-256 digest of `.dart_tool/package_config.json`, and, after handshake, the extension's cached `ToolExtensionCapabilities`). Invalidating whenever a `.dill.d` source input (other than `.dart_tool/package_config.json`, which is validated by content hash) has a modification timestamp at or after `compiledAt` (rather than comparing against `extension.dill`'s modification time) ensures that source edits saved while `dart compile kernel` is still in flight invalidate the snapshot on the next run, even on filesystems with millisecond or 1-second timestamp granularity. Hashing the raw `.dart_tool/package_config.json` bytes alongside the SDK revision deterministically invalidates cached snapshots across `hosted` version changes, `git` ref updates (`$PUB_CACHE/git/<package>-<sha>`), `path:` or `dependency_overrides` changes, and `fvm` or SDK switches whose unpacked archive timestamps predate `compiledAt`, while avoiding unnecessary recompilation on no-op `pub get` runs with identical `package_config.json` contents and remaining future-proof as Pub evolves its internal metadata files.
* **Capability Freshness Ordering & Concurrency**: During discovery, the host runs the `extension.dill.stamp` and `.dill.d` freshness check **before** applying the cached-capability filter, treating stale snapshots as having unknown capabilities. Under a cross-process lockfile, compilation atomically renames `.dill.d`, then `extension.dill`, and finally `extension.dill.stamp` (with a fresh `buildToken` and cleared capabilities) last so the stamp acts as the linearizable commit point, and `writeCachedCapabilities` only records capabilities when the on-disk stamp still matches the `buildToken` returned by `compile()`. Adding a new `*Service` to a local extension is therefore picked up immediately on the next `flutter doctor` or `flutter build` invocation without risking cross-process capability races. Cross-workspace shared `.dill` caching is deferred as a potential future optimization if cold per-workspace compilation ever proves noticeable in multi-project or ephemeral CI workflows.

### 3. Isolate Transport, Lifecycle & Isolation Boundaries

#### 3.1 JSON-RPC 2.0 Transport, Handshake & Exit Monitoring

```mermaid
sequenceDiagram
  participant Host as Flutter Tool (Host Isolate)
  participant Iso as Extension Isolate (ToolExtensionEntryPoint)
  participant Svc as Registered ToolExtensionServices

  Host->>Iso: Isolate.spawnUri(dillUri, [], handshakeSendPort, onError, onExit)
  Iso->>Svc: await service.initialize() (skipped if supportedHostPlatforms excludes host)
  Note over Iso: Connect IsolateChannel only after fallible setup succeeds
  Iso->>Host: IsolateChannel.connectSend(handshakeSendPort)
  Iso->>Svc: Wire notificationSender & requestSender to Peer
  Note over Host,Iso: Bidirectional IsolateChannel + Peer.withoutJson
  Host->>Iso: RPC "extension.getCapabilities"
  Iso-->>Host: ToolExtensionCapabilities (services, supportedHostPlatforms)
  Host->>Host: Cache capabilities, shut down if host unsupported
  Note over Host,Iso: Active Command RPCs & Notifications
  Host->>Iso: RPC "extension.shutdown"
  Iso->>Svc: await Future.wait(services.map((s) => s.shutdown())) (if initialized)
  Iso-->>Host: { "acknowledged": true }
  Host->>Iso: peer.close() & isolate.kill(priority: Isolate.immediate)
```

Because both endpoints execute inside the same Dart VM process, the Flutter Tool and `ToolExtensionEntryPoint` communicate over a `Peer.withoutJson` backed by an `IsolateChannel<Object?>`. Structured `Map<String, Object?>` payloads cross the isolate port directly without intermediate UTF-8 string encoding or decoding while preserving standard JSON-RPC 2.0 request, response, and notification framing.

When an extension isolate boots on a supported host platform, `ToolExtensionEntryPoint.run` invokes `await service.initialize()` on every registered service **before** calling `IsolateChannel.connectSend(sendPort)`. Because `connectSend` opens a `ReceivePort` that keeps the isolate alive, deferring channel connection until after all fallible initialization completes ensures that an unhandled exception during `initialize()` allows the isolate to exit immediately. When `supportedHostPlatforms` is non-null and excludes the current host platform, `ToolExtensionEntryPoint.run` skips `service.initialize()`, connects the `IsolateChannel` to serve `extension.getCapabilities` so the host records the cached capabilities, and awaits clean shutdown. On the host side, the tool attaches listeners to `Isolate.spawnUri`'s `onError` and `onExit` ports so unexpected isolate termination immediately fails any pending handshake or in-flight RPCs.

**Wire Payload Examples**:

1. **Capability Handshake Request**: Sent by the Flutter Tool to the extension isolate immediately after the `IsolateChannel` connects to query which services and host platforms the extension declares:

   ```json
   {
     "jsonrpc": "2.0",
     "id": 1,
     "method": "extension.getCapabilities"
   }
   ```

2. **Capability Handshake Response**: Returned by the extension isolate listing the active service namespaces and optional `supportedHostPlatforms` (serialized as a `List<String>` of `HostPlatform.cliName` values such as `linux-x64`, `linux-arm64`, `linux-riscv64`, `darwin-x64`, `darwin-arm64`, `windows-x64`, or `windows-arm64`, and omitted when unrestricted/`null`):

   ```json
   {
     "jsonrpc": "2.0",
     "id": 1,
     "result": {
       "services": ["build", "device", "template"],
       "supportedHostPlatforms": [
         "darwin-arm64",
         "darwin-x64",
         "linux-arm64",
         "linux-x64"
       ]
     }
   }
   ```

3. **Structured Log Notification**: Sent asynchronously by the extension isolate to stream log output to the Flutter Tool's logger (`timestamp` is an optional ISO-8601 UTC string on `'extension.log'` notifications; `ExtensionLogMessage.timestamp` is `DateTime?`, populated automatically by `ToolExtensionService.log`):

   ```json
   {
     "jsonrpc": "2.0",
     "method": "extension.log",
     "params": {
       "level": "info",
       "message": "Launching /path/to/bundle on embedder-01..."
     }
   }
   ```

Shared JSON-RPC 2.0 method and notification identifiers live in `package:flutter_tools_core` so both host adapters in `package:flutter_tools` and isolate base services in `package:flutter_tools_extension` reference a single wire catalog:

```dart
// package:flutter_tools_core/src/rpc_methods.dart
/// Wire method and notification names shared across the JSON-RPC 2.0 channel.

  /// Graceful shutdown request sent by the host (`'extension.shutdown'`).

  /// Structured log notification sent to the host (`'extension.log'`).
  static const log = 'extension.log';

  /// Progress status notification sent to the host (`'extension.progress'`).
  static const progress = 'extension.progress';

  /// extension (`'extension.getConfigurationValues'`).
  static const getConfigurationValues = 'extension.getConfigurationValues';

  /// Host callback rendering a Mustache template directory into the project or
  /// build directory (`'extension.renderTemplate'`).
  static const renderTemplate = 'extension.renderTemplate';

  /// Host callback reading a line of terminal input (`'terminal.promptForInput'`).
  static const promptForInput = 'terminal.promptForInput';

  /// Host callback presenting a numbered terminal menu (`'terminal.promptForOption'`).
  static const promptForOption = 'terminal.promptForOption';

  /// Device log line notification sent to the host (`'device.logEntry'`).
  static const deviceLogEntry = 'device.logEntry';

}
```

#### 3.2 Graceful Shutdown & Subprocess Cleanup

Extensions frequently spawn OS subprocesses (such as `ssh -L` port-forwarding tunnels, device log readers, or emulators) whose lifecycles must not outlive the `flutter` process:

* The tool registers extension teardown with its shutdown hooks on CLI exit.
* When shutting down an active extension, the tool sends an `extension.shutdown` RPC to the isolate and awaits completion with a short bounded grace period before closing the JSON-RPC `Peer` and calling `isolate.kill(priority: Isolate.immediate)`, ensuring a wedged extension cannot hang CLI exit.
* `ToolExtensionEntryPoint` handles `extension.shutdown` by invoking `await Future.wait(initializedServices.map((s) => s.shutdown()))` on every initialized service (skipping `shutdown()` when `service.initialize()` was skipped on an excluded host), allowing `DeviceService.shutdown()` and other services to terminate active tunnels and child processes cleanly.
* For hermetic unit testing, extensions inject standard `package:process` `ProcessManager` and `package:file` `FileSystem` dependencies via their service and target constructors (see [Testing Plan](#testing-plan)). Because OS child processes belong to the host VM process rather than the child isolate, background subprocess PIDs spawned by an extension can also be reported to the host tool so unexpected isolate exits still clean up remaining child processes via `Process.killPid`.

#### 3.3 Isolate Isolation Boundaries & Process-Wide Constraints

While Dart isolates provide separate heaps and prevent uncaught Dart exceptions in an extension from crashing the main tool isolate's event loop, **isolates share the same OS process** as the Flutter Tool. Extension authors and the host runtime must account for four process-wide boundaries:

1. **`stdout` / `stderr` / `stdin` Stream Integrity**: Commands such as `flutter daemon` and `flutter devices --machine` emit structured JSON protocol frames over `stdout`. Unintercepted writes to `io.stdout` or `print()` calls inside an extension isolate would corrupt the tool's machine output, and reads from `io.stdin` would contend with the host CLI for terminal input.
   * **Mitigation**: `ToolExtensionService.log` emits structured `extension.log` JSON-RPC notifications that the host forwards to its logger. In addition, `ToolExtensionEntryPoint.run` executes inside both a custom `ZoneSpecification` (intercepting `print()` calls) and `IOOverrides.runZoned` (overriding `stdout`, `stderr`, and `stdin`). Any direct writes to `io.stdout` or `io.stderr` inside the extension isolate are captured by the overridden `stdout` and `stderr` streams and forwarded as `extension.log` JSON-RPC notifications (`level: .info` and `level: .error`), while `io.stdin` is overridden with an empty stream so extensions cannot block waiting on raw terminal input (interactive CLI prompts are instead mediated by the host tool over the bidirectional JSON-RPC `Peer`; see [Section 4.3](#43-configuration-flutter-config)).
2. **Process Exit & Working Directory**: Calling `io.exit()` inside an extension terminates the entire `flutter` process immediately, and mutating `io.Directory.current` alters the process-wide current working directory for the main isolate and sibling extensions.
   * **Mitigation**: The `IOOverrides.runZoned` environment installed by `ToolExtensionEntryPoint.run` also overrides `exit` (`exit: (int code) => throw UnsupportedError('Tool extensions must not call exit().')`, using the `IOOverrides.exit` hook added in Dart 3.10) and guards `getCurrentDirectory` / `setCurrentDirectory` against working-directory mutations. Instead of calling `exit()` or mutating `Directory.current`, extensions must throw `ToolExtensionException` on failure, pass explicit `workingDirectory` arguments when spawning processes, and resolve paths against project URIs.
3. **Native Crashes (FFI) and Out-of-Memory**: A segmentation fault in native FFI code loaded by an extension or process-level memory exhaustion will terminate the `flutter` process.
4. **Snapshot Format Compatibility (`Isolate.spawnUri`)**: The snapshot format passed to `Isolate.spawnUri` must match the execution mode of the host Dart runtime. Because the Flutter Tool currently executes on the Dart JIT VM, the tool compiles extensions into kernel (`.dill`) snapshots (`dart compile kernel`). If the Flutter Tool is compiled into a standalone AOT executable (`dart compile exe`), `Isolate.spawnUri` cannot load kernel `.dill` files, but it *can* spawn precompiled AOT snapshots (`dart compile aot-snapshot`) compiled with the matching Dart runtime. (See [Alternatives Considered](#alternatives-considered) for `stdio` subprocess trade-offs.)

### 4. Base Service Contracts & Host Integration

#### 4.1 Core Service, Entrypoint & Error Abstractions

`package:flutter_tools_extension` provides a set of base classes for the services that can be implemented by an extension. All seven extension services (`DiagnosticsService`, `ConfigService`, `TemplateService`, `DeviceService`, `BuildService`, `ArtifactService`, and `CleanService`), as well as `BuildTarget` and `AssembleTarget`, are declared as `abstract base class`. Restricting `implements` ensures that `package:flutter_tools_extension` can add new defaulted methods in minor releases without breaking existing extensions. JSON-RPC namespace, method, and parameter wire constants live in `package:flutter_tools_core` (`ExtensionRpcMethods`), and RPC handler registration runs internally inside `ToolExtensionEntryPoint.run`, keeping public `*Service` classes scoped strictly to lifecycle hooks (`initialize` and `shutdown`), `@nonVirtual` host callbacks (`log`, `reportProgress`, `getConfigurationValues`, `promptForInput`, `promptForOption`, `BuildService.renderTemplate`, and `DeviceService.emitLogLine`), and overridable domain members.

To replace the current ad-hoc error handling (where extensions throw generic exceptions or `RpcException` directly), this RFC proposes a single structured error model in `package:flutter_tools_core`: actionable domain errors (such as missing target SDKs, failed native compiler invocations, or unreachable devices) throw `ToolExtensionException` (with default error code `-32001`), optional capabilities that are not supported throw `UnsupportedError` (mapped to JSON-RPC error code `-32002`), and unexpected uncaught exceptions map to `json_rpc_2`'s standard `-32000` (`SERVER_ERROR`), allowing the tool to distinguish actionable domain errors from unhandled extension bugs.

```dart
// package:flutter_tools_core/src/exception.dart
/// An exception thrown by a tool extension to report an intentional,
/// user-actionable domain error over JSON-RPC 2.0.
@immutable
class ToolExtensionException implements Exception {
  /// Creates a domain exception with a user-facing [message], optional JSON-RPC
  /// error [code], and optional structured diagnostic [data].
  const ToolExtensionException(
    this.message, {
    this.code = domainErrorCode,
    this.data,
  });

  /// JSON-RPC error code for intentional, user-actionable domain errors.
  /// Distinct from -32000 (`SERVER_ERROR`), which indicates an unhandled
  /// exception in the extension isolate.
  static const domainErrorCode = -32001;

  /// JSON-RPC error code returned when an optional capability is not supported
  /// by the extension.
  static const unsupportedCapabilityErrorCode = -32002;

  /// The JSON-RPC 2.0 error code reported to the Flutter Tool.
  final int code;

  /// Optional structured error details serialized into the JSON-RPC error data.
  final Map<String, Object?>? data;

  /// Human-readable error message surfaced by the Flutter Tool.
  final String message;
}
```

```dart
// package:flutter_tools_extension/src/protocol_base/service.dart
/// Base class for all services exposed by a Flutter Tool extension isolate.
abstract base class ToolExtensionService {
  /// Initializes any state needed by the service before the isolate connects
  /// its JSON-RPC peer channel.
  Future<void> initialize() async {}

  /// Cleans up resources held by the service when the extension is shut down.
  Future<void> shutdown() async {}

  /// Sends a fire-and-forget JSON-RPC 2.0 notification to the host tool.
  /// Throws a [StateError] if called before the peer channel is connected.
  // Wired internally by ToolExtensionEntryPoint.run.
  @nonVirtual
  external void sendNotification(
    String method, [
    Map<String, Object?>? parameters,
  ]);

  /// Sends a structured `extension.log` notification to the host tool.
  ///
  /// On `'extension.log'` notifications, `timestamp` (an ISO-8601 UTC string;
  /// `ExtensionLogMessage.timestamp` is `DateTime?`) is optional and populated
  /// automatically by [log].
  @nonVirtual
  void log(
    String message, {
    ExtensionLogLevel level = .info,
    DateTime? timestamp,
  }) {
    sendNotification(ExtensionRpcMethods.log, <String, Object?>{
      'level': level.name,
      'message': message,
      'timestamp': (timestamp ?? DateTime.now()).toUtc().toIso8601String(),
    });
  }

  /// Emits an `extension.progress` notification to report progress for
  /// long-running operations to the host tool.
  @nonVirtual
  void reportProgress(String message) {
    sendNotification(ExtensionRpcMethods.progress, <String, Object?>{
      'message': message,
    });
  }

  /// Sends a JSON-RPC 2.0 request to the host tool over the bidirectional
  /// `Peer` and returns the decoded result payload.
  // Wired internally by ToolExtensionEntryPoint.run.
  @protected
  @nonVirtual
  external Future<Object?> sendHostRequest(
    String method,
    Map<String, Object?> params,
  );

  /// Queries the host tool over the bidirectional JSON-RPC `Peer` for the
  /// persisted `flutter config` values owned by this extension (`bool` for
  /// declared `FeatureFlag.settingName` keys, `String` for declared
  /// `ConfigOption.name` and `ConfigAction.settingsKeys`), omitting unset
  /// keys.
  @nonVirtual
  Future<Map<String, Object?>> getConfigurationValues() async {
    final Object? response = await sendHostRequest(
      ExtensionRpcMethods.getConfigurationValues,
      const <String, Object?>{},
    );
    if (response case final Map<String, Object?> map) {
      return map;
    }
    throw FormatException(
      'Expected Map<String, Object?> from '
      '"${ExtensionRpcMethods.getConfigurationValues}", got '
      '${response.runtimeType}.',
      response,
    );
  }

  /// Prompts the user to enter a line of text via the host tool's interactive
  /// terminal over the bidirectional JSON-RPC peer.
  ///
  /// When [echo] is `false`, the host disables terminal character echoing
  /// while reading the line (for pairing passphrases or PINs). Returns the
  /// entered text (including `''` or [defaultValue]), or `null` if the user
  /// cancels input (EOF). Throws a [ToolExtensionException] if the host tool
  /// is running without an interactive terminal or with `--machine`.
  @nonVirtual
  Future<String?> promptForInput({
    required String message,
    String? defaultValue,
    bool echo = true,
  }) async {
    final Object? response = await sendHostRequest(
      ExtensionRpcMethods.promptForInput,
      <String, Object?>{
        'message': message,
        'defaultValue': ?defaultValue,
        'echo': echo,
      },
    );
    if (response case {'value': final String? value}) {
      return value;
    }
    throw FormatException(
      'Expected {"value": String?} from '
      '"${ExtensionRpcMethods.promptForInput}", got ${response.runtimeType}.',
      response,
    );
  }

  /// Prompts the user to select an option from [options] via the host tool's
  /// interactive terminal over the bidirectional JSON-RPC peer.
  ///
  /// Returns the selected 0-based index in [options], or `null` if the user
  /// cancels the prompt. Throws a [ToolExtensionException] if the host tool is
  /// running without an interactive terminal or with `--machine`.
  @nonVirtual
  Future<int?> promptForOption({
    required String message,
    required List<String> options,
    int? defaultChoiceIndex,
  }) async {
    final Object? response = await sendHostRequest(
      ExtensionRpcMethods.promptForOption,
      <String, Object?>{
        'message': message,
        'options': options,
        'defaultChoiceIndex': ?defaultChoiceIndex,
      },
    );
    if (response case {'selectedIndex': final int? selectedIndex}) {
      return selectedIndex;
    }
    throw FormatException(
      'Expected {"selectedIndex": int?} from '
      '"${ExtensionRpcMethods.promptForOption}", got ${response.runtimeType}.',
      response,
    );
  }
}
```

#### 4.3 Configuration (`flutter config`)

To support custom configuration options, extensions can provide an implementation of `ConfigService`, which allows extensions to add boolean feature flags (`--[no-]enable-<flag>`), key-value configuration options (`--<option>=<value>`), and action flags (`--<action>`) to `flutter config`. For declarative flags and key-value options, the Flutter Tool dynamically registers them on the `flutter config` argument parser, groups them under `<title> (package:<extension_name>)` in `flutter config --help` and `flutter config --list`, and persists values in Flutter's global settings file (for example, `~/.config/flutter/settings` on Linux and macOS).

In addition to declarative flags and key-value options, platforms such as iOS and macOS require action-based and interactive configuration workflows in `flutter config` (for example, `flutter config --select-ios-signing-settings`, which walks the user through selecting a code-signing certificate or provisioning profile via interactive terminal prompts, and `flutter config --clear-ios-signing-settings`, which clears multiple saved settings without taking a CLI value). `ConfigService` supports these workflows without giving extension isolates direct access to `io.stdin`:

* **Action Registration (`getConfigActions`)**: Extensions declare `ConfigAction` entries (with `name`, `help`, optional `aliases`, and `settingsKeys`), which the Flutter Tool registers as non-negatable boolean action flags on `flutter config`. `ConfigAction.settingsKeys` declares the configuration keys managed by the action so the tool can display their saved values under the extension's section in `flutter config --list` without exposing them as standalone `--<key>=<value>` CLI flags.
* **Action Execution & Persistence (`runConfigAction`)**: When the user invokes `flutter config --<action>`, the tool calls `runConfigAction(name, currentSettings: ...)` (scoping `currentSettings` to the extension's declared `ConfigOption` names and `ConfigAction.settingsKeys`), validates that all keys in the returned `Map<String, String?>` belong to those declared keys, and applies the updates to Flutter's configuration store (persisting non-null string values and removing keys mapped to `null`).
* **Host-Mediated Interactive Prompts (`terminal.promptForOption` & `terminal.promptForInput`)**: When an action needs interactive user input, the extension calls `promptForOption(...)` (for numbered menu selections) or `promptForInput(...)` (for free-form text or `echo: false` passphrase entry) on `ToolExtensionService` over the bidirectional `Peer`. In both cases, the host tool verifies `terminal.stdinHasTerminal` (failing fast with a `ToolExtensionException` if invoked non-interactively or with `--machine`) and returns the user's selection or text (or `null` if the user cancels the prompt). This allows interactive hardware setup and device pairing workflows (such as prompting for a device address and an ephemeral on-screen pairing passphrase via `promptForInput(..., echo: false)` to exchange SSH keys) to run directly inside `flutter config` without requiring users to invoke a separate vendor CLI tool. Extensions managing multi-device or structured connection inventories should persist those records in an extension-managed configuration file (under `$DART_DATA_HOME/<extension>/` or at a path configured via `ConfigOption`) so interactive `ConfigAction` flows can update it while CI and headless environments can configure devices declaratively. Such extension-managed device inventory files are runtime `DeviceService` state and must not be read as untracked inputs inside `BuildTarget.build` or `AssembleTarget.build` (any file read during `flutter assemble` must be declared via `ExtensionPatternSource`).

At runtime, `ToolExtensionService` subclasses (`DiagnosticsService`, `ArtifactService`, `DeviceService`, and `TemplateService`) read persisted configuration values by calling `getConfigurationValues()` (`extension.getConfigurationValues`) over the bidirectional JSON-RPC `Peer`. By contrast, because `BuildTarget` and `AssembleTarget` are not `ToolExtensionService` subclasses and `AssembleTarget.build` must not read untracked inputs over ad-hoc RPCs (which would bypass `flutter assemble` incremental cache invalidation), build and assemble targets receive the extension's persisted settings directly via `ExtensionBuildContext.configuration`, which the host hashes into the `flutter assemble` environment inputs so configuration changes automatically invalidate cached build outputs.

To keep global persistence, CLI flag namespaces, and out-of-project `flutter config` usage unambiguous:

* **Namespaced `"extensions"` Settings JSON Schema**: Persisted extension settings are stored under a dedicated top-level `"extensions"` map keyed by extension package name in Flutter's global settings file, isolating extension keys from built-in Flutter `Config` keys and from other extensions while filtering `getConfigurationValues()` and `ExtensionBuildContext.configuration` strictly to keys declared by that extension's `ConfigService` (`FeatureFlag.settingName` mapped to `bool`, and `ConfigOption.name` and `ConfigAction.settingsKeys` mapped to `String`, omitting unset keys):

  ```json
  {
    "android-sdk": "/opt/android-sdk",
    "enable-tool-extensions": true,
    "extensions": {
      "flutter_tizen_tools": {
        "tizen-sdk": "/opt/tizen-studio",
        "enable-tizen-dotnet": true
      }
    }
  }
  ```

  When first-party platforms migrate existing top-level `flutter config` settings (such as `ios-signing-cert`), `ConfigOption.aliases` (or legacy top-level fallback) preserves backward-compatible reads while new extension keys remain isolated under `"extensions"`.
* **Platform-Prefixed CLI Flag Convention & Deterministic Collision Handling**: Because `flutter config` shares a single flat `ArgParser` across built-in flags and all active extensions in a workspace, extensions should prefix configuration keys and actions with their platform name (`--<platform>-<setting>`, `--[no-]enable-<platform>-<feature>`, `--select-<platform>-*`, `--clear-<platform>-*`). Built-in `ConfigCommand` and global `FlutterCommandRunner` flags always take precedence (emitting a visible warning naming the offending extension package and skipping the colliding registration), and collisions between two active extensions resolve deterministically in lexicographical `<package_name>` order (keeping the first extension's registration, emitting a visible warning naming both packages, and skipping the duplicate).
* **Outside-Project `flutter config` UX**: Because extension flags are registered by project-scoped extensions whereas Flutter's global settings file is machine-wide:
  * Running `flutter config --list` (or `flutter config` with no arguments) outside a Flutter project (or in a project where a previously configured extension is inactive) still reads the `"extensions"` JSON map and displays previously saved extension values grouped by `<package_name>` under `Saved Extension Settings (inactive outside project):`, rather than hiding saved settings or leaking raw keys into `All Settings:`.
  * When `flutter config` fails `ArgParser` lookup on an unknown `--<flag>` outside a project (or when no active extension registers that flag), the error message appends a hint explaining that extension configuration flags are provided by project extensions and must be run inside a Flutter project or Pub workspace declaring that extension.

#### 4.4 Platform Templates & Scaffolding (`flutter create`)

To integrate with `flutter create`, extensions can implement `TemplateService`. This service allows embedder maintainers to supply platform-specific runner templates that augment standard application and plugin projects. To support both single-command project creation and incremental platform additions without a global extension registry, `flutter create` adds two CLI options:

* **`--extension=<package[@descriptor]>`**: A repeatable multi-option (`addMultiOption('extension', splitCommas: false)`, hidden from `--help` when `enable-tool-extensions` is disabled) that bootstraps one or more extension packages into `<target_dir>`'s `dev_dependencies` via `pub add`, compiles their workspace-local `extension.dill` snapshots, and renders their `TemplateService` platform templates in a single command. It accepts standard `dart pub add` package descriptors (such as `flutter_custom_tools`, `flutter_custom_tools@^1.2.0`, `'flutter_custom_tools@{path: ../flutter_custom_tools}'`, and `'flutter_custom_tools@{git: {url: https://..., ref: main}}'`; `splitCommas: false` preserves commas inside YAML flow descriptors), normalizes entries to `dev:<package>` while rejecting `override:` prefixes, and runs `pub add --directory <target_dir>` through the tool's `Pub` wrapper from the caller's working directory so relative `{path: ...}` descriptors resolve against the caller's directory. `--extension` is supported on both brand-new projects and existing projects (including existing `resolution: workspace` members).
* **`--no-platforms`**: A non-negatable boolean flag (`addFlag('no-platforms', negatable: false)`, mutually exclusive with `--platforms`) that scaffolds only the shared Dart project skeleton (`pubspec.yaml`, `lib/`, `test/`) without generating built-in platform directories (usable either standalone or alongside `--extension` when pre-installing an extension without scaffolding platform runners).

```dart
/// The service responsible for adding custom platform support to
/// `flutter create` for `app`, `plugin`, and `plugin_ffi` projects.
abstract base class TemplateService extends ToolExtensionService {
  /// Custom boolean CLI flags registered on `flutter create` and passed in
  /// `toolParameters['templateFlags']`.
  List<ExtensionFlag> get flags => const <ExtensionFlag>[];

  /// Custom single-value CLI options registered on `flutter create` and passed
  /// in `toolParameters['templateOptions']` (for example,
  /// `--tizen-language=cpp|csharp` or `--app-type=ui|service|multi`).
  ///
  /// Entries must not set [ExtensionOption.mandatory] to `true`.
  List<ExtensionOption> get options => const <ExtensionOption>[];

  /// Map of custom platform identifiers to `package:` URIs pointing to
  /// application platform runner template directories rendered when
  /// `flutter create . --platforms=<platform>` is invoked.
  Map<String, String> get appPlatformTemplates => const <String, String>{};

  /// Map of custom platform identifiers to `package:` URIs pointing to
  /// plugin platform template directories rendered for plugin projects
  /// (`flutter create . -t plugin --platforms=<platform>`).
  Map<String, String> get pluginPlatformTemplates => const <String, String>{};

  /// Map of custom platform identifiers to `package:` URIs pointing to FFI
  /// plugin platform template directories rendered for FFI plugin projects
  /// (`flutter create . -t plugin_ffi --platforms=<platform>`).
  Map<String, String> get ffiPluginPlatformTemplates =>
      const <String, String>{};

  /// Custom platform identifiers supported for `-t app` projects, surfaced in
  /// `flutter create --help`, `--platforms` validation, and
  /// `verifyExtensionPackage`.
  ///
  /// Defaults to the keys of [appPlatformTemplates]; extensions overriding
  /// [resolvePlatformTemplate] for dynamic multi-variant templates without
  /// populating [appPlatformTemplates] override this getter directly.
  Set<String> get appPlatforms => appPlatformTemplates.keys.toSet();

  /// Custom platform identifiers supported for `-t plugin` projects, surfaced
  /// in `flutter create --help`, `--platforms` validation, and
  /// `verifyExtensionPackage`.
  ///
  /// Defaults to the keys of [pluginPlatformTemplates]; extensions overriding
  /// [resolvePlatformTemplate] without populating [pluginPlatformTemplates]
  /// override this getter directly.
  Set<String> get pluginPlatforms => pluginPlatformTemplates.keys.toSet();

  /// Custom platform identifiers supported for `-t plugin_ffi` projects,
  /// surfaced in `flutter create --help`, `--platforms` validation, and
  /// `verifyExtensionPackage`.
  ///
  /// Defaults to the keys of [ffiPluginPlatformTemplates]; extensions
  /// overriding [resolvePlatformTemplate] without populating
  /// [ffiPluginPlatformTemplates] override this getter directly.
  Set<String> get ffiPluginPlatforms =>
      ffiPluginPlatformTemplates.keys.toSet();

  /// Resolves the platform template descriptor for [platform] and
  /// [templateType] using the parsed [toolParameters].
  ///
  /// Defaults to looking up [platform] in [appPlatformTemplates],
  /// [pluginPlatformTemplates], or [ffiPluginPlatformTemplates]. Extensions
  /// with multiple template variants (such as C++ vs. C# or UI vs. background
  /// service app templates) can override this method to validate platform
  /// options, select a template directory, specify shared project files in
  /// [ExtensionPlatformTemplate.overwritePaths] (such as `'lib/main.dart'`),
  /// or declare additional pub dependencies in
  /// [ExtensionPlatformTemplate.dependencies].
  Future<ExtensionPlatformTemplate?> resolvePlatformTemplate({
    required String platform,
    required ExtensionTemplateType templateType,
    required Map<String, Object?> toolParameters,
  }) async {
    final String? rawUri = switch (templateType) {
      .app => appPlatformTemplates[platform],
      .ffiPlugin => ffiPluginPlatformTemplates[platform],
      .plugin => pluginPlatformTemplates[platform],
    };
    if (rawUri == null) {
      return null;
    }
    return ExtensionPlatformTemplate(templateUri: Uri.parse(rawUri));
  }

  /// Generates or augments the map of parameters to values used to populate
  /// Mustache template variables when rendering [platform] during
  /// `flutter create . --platforms=<platform>`.
  ///
  /// Defaults to returning [toolParameters] unchanged.
  Future<Map<String, Object?>> generatePlatformTemplateParameters({
    required String platform,
    required Map<String, Object?> toolParameters,
  }) async => toolParameters;

  /// Returns the platform configuration map (for example, `pluginClass`,
  /// `dartPluginClass`, or `ffiPlugin`) to merge under
  /// `flutter.plugin.platforms.<platform>` in `pubspec.yaml` when scaffolding
  /// a plugin via `flutter create . -t plugin --platforms=<platform>` or
  /// `flutter create . -t plugin_ffi --platforms=<platform>`, or `null` if no
  /// `pubspec.yaml` update is needed.
  Future<Map<String, Object?>?> generatePluginPlatformConfig({
    required String platform,
    required ExtensionTemplateType templateType,
    required Map<String, Object?> toolParameters,
  }) async => null;
}
```

Host integration with `TemplateService` during `flutter create` follows these steps:

* **Target-Directory Discovery Scope & Pub Workspaces**: `CreateCommand` scopes extension discovery strictly to `<target_dir>` rather than the caller's working directory so extensions declared in an unrelated enclosing directory never leak into a newly created standalone project. Newly created directories remain standalone (without mutating parent Pub workspace `pubspec.yaml` files), while in-place `flutter create .` on an existing project or `resolution: workspace` member inherits workspace-root `dev_dependencies`.
* **Two-Stage In-Place Bootstrap (`--extension`)**: When `--extension=<package[@descriptor]>` is passed on `flutter create`:
  * **Pre-flight checks & `--help` behavior**: `flutter create --help` (even when `--extension=...` is passed on the command line) stays offline and side-effect-free, skipping bootstrap and therefore omitting extension-specific `ExtensionFlag` and `ExtensionOption` entries until the project is created. Passing `--extension` when `enable-tool-extensions` is disabled fails immediately with an actionable error instructing the user to run `flutter config --enable-tool-extensions`. Likewise, combining `--extension` with `--no-pub` or `--no-extensions` (`FLUTTER_NO_EXTENSIONS=1`) fails immediately before modifying disk.
  * **Pass-1 CLI parsing**: Parses known `CreateCommand` options (`--extension`, `--platforms` with `allowed: null`, `-t`, `--org`, `--pub`, `--offline`, `--overwrite`, etc.) and `<output directory>` deterministically before touching disk while requiring `--<option>=<value>` syntax for unknown extension `ExtensionOption`s (for example, `--app-type=service <dir>`) and treating bare unknown `--<flag>` / `--no-<flag>` tokens as boolean `ExtensionFlag`s (for example, `--custom-wearable <dir>`), deferring validation of those unknown flags and options to Pass 2 (space-separated `--<option> <value>` continues to work when running `flutter create .` inside an already-bootstrapped project where `TemplateService` loads before argument parsing).
  * **Base scaffold, `pub add`, & workspace-local `.dill` compilation**: Scaffolds the base project skeleton into `<target_dir>` when creating a new project (on an existing project, pre-existing files are snapshotted before mutation as described below), runs `pub add --directory <target_dir> [--offline] dev:<package>...` from the caller's working directory (forwarding `--offline` when specified), compiles `<workspace>/.dart_tool/flutter_tools/extensions/<package>/extension.dill` (alongside `.d` and `.stamp`, where `<workspace>` is the Pub workspace root or `<target_dir>` if standalone) so subsequent commands hit a warm snapshot, spawns the extension isolate, and queries `TemplateService` (`*Platforms`, `flags`, and `options`).
  * **Pass-2 CLI validation & default `--platforms` selection**: Rebuilds `CreateCommand`'s `ArgParser` with the discovered `ExtensionFlag` and `ExtensionOption` definitions to strictly validate all CLI arguments and `--platforms`. On both new and existing projects, when neither `--platforms` nor `--no-platforms` is specified on `-t app`, `-t plugin`, or `-t plugin_ffi`, `flutter create --extension=...` defaults to scaffolding only the platform(s) advertised by the bootstrapped extension(s) for that archetype (`appPlatforms`, `pluginPlatforms`, or `ffiPluginPlatforms`), falling back to built-in default `--platforms` behavior only if the bootstrapped extension(s) advertise no platforms for that archetype (avoiding unintended regeneration of all six built-in platforms when adding an extension to an existing app).
  * **Follow-up `pub get` & failure rollback**: After rendering custom platform templates, `flutter create` runs a follow-up local `pub get` (respecting `--offline`) only if `ExtensionPlatformTemplate.dependencies` or `generatePluginPlatformConfig` modified `pubspec.yaml` (and in `example/` when standalone `example/pubspec.yaml` was updated). On an existing project, before mutating files, `flutter create` snapshots `<target_dir>/pubspec.yaml`, `<workspace>/pubspec.lock` (if present), `example/pubspec.yaml` (if present), and any pre-existing files targeted by `overwritePaths` or `--overwrite`. If `pub add`, `.dill` compilation, Pass-2 argument validation, template rendering, or follow-up `pub get` fails, `flutter create` deletes `<target_dir>` if newly created, removes newly written entries if `<target_dir>` pre-existed as an empty directory, or restores all snapshotted files, removes newly created files, and runs best-effort `pub get --offline` to reconcile `.dart_tool/` on an existing project (logging a warning if offline reconciliation fails without masking the original error).
* **Platform Discovery & Origin Attribution (`appPlatforms`, `pluginPlatforms`, `ffiPluginPlatforms`)**: `flutter create` queries active `TemplateService` extensions for `appPlatforms`, `pluginPlatforms`, and `ffiPluginPlatforms` (defaulting to the keys of `appPlatformTemplates`, `pluginPlatformTemplates`, and `ffiPluginPlatformTemplates`) so extensions overriding `resolvePlatformTemplate` for multi-variant templates can advertise their supported platform identifiers to `flutter create --help` (inside an existing project or Pub workspace, annotated with `(package:<extension_name>)`) and `--platforms` validation without supplying placeholder URIs. Built-in platform identifiers (`android`, `ios`, `web`, `linux`, `macos`, `windows`) always take precedence (emitting a visible warning naming the offending extension package and skipping the colliding platform), and custom platform collisions between two active extensions resolve deterministically in lexicographical `<package_name>` order (keeping the first extension's platform, emitting a visible warning naming both packages, and skipping the duplicate).
* **Custom `flutter create` CLI Flags & Options (`flags` & `options`)**: When running inside an existing project without `--extension`, `flutter create` queries active `TemplateService` extensions before parsing arguments; when bootstrapping via `--extension`, `flutter create` registers them during Pass-2 validation after `pub add` resolves the extension. In both flows, `flutter create` registers `flags` (`ExtensionFlag`) and `options` (`ExtensionOption`) on its `ArgParser` (attributing their `--help` descriptions with `(package:<extension_name>)`) and includes the parsed maps under `toolParameters['templateFlags']` (`Map<String, bool>`) and `toolParameters['templateOptions']` (`Map<String, String>`) alongside standard template parameters (`projectName`, `description`, `organization`, `androidLanguage`, `iosLanguage`, etc.). Built-in `CreateCommand` options and global `FlutterCommandRunner` flags (`-d`, `-v`, `-h`, etc.) always take precedence over colliding long names (`name`) or short aliases (`abbr`) (emitting a visible warning naming the offending extension package and skipping the colliding registration), and collisions between two active extensions resolve deterministically in lexicographical `<package_name>` order (keeping the first extension's registration, emitting a visible warning naming both packages, and skipping the duplicate). Because `CreateCommand` shares a single `ArgParser` across all target platforms, `TemplateService.options` rejects entries with `ExtensionOption.mandatory == true` (at host registration time, since a mandatory option would otherwise break unrelated commands such as `flutter create . --platforms=linux` whenever the extension is active); extensions validate any platform-required options inside `resolvePlatformTemplate` when their platform is requested.
* **Dynamic Multi-Variant Template Resolution, Selective Overwrite, & Extra Dependencies (`resolvePlatformTemplate`)**: When `flutter create` scaffolds a custom platform (for `-t app`, `-t plugin`, or `-t plugin_ffi`, either via `--extension` or in-place `--platforms=<platform>`), the tool calls `resolvePlatformTemplate(platform: platform, templateType: ..., toolParameters: ...)` (defaulting to `appPlatformTemplates[platform]`, `pluginPlatformTemplates[platform]`, or `ffiPluginPlatformTemplates[platform]`). The tool resolves `ExtensionPlatformTemplate.templateUri` against `.dart_tool/package_config.json` and renders its Mustache templates into the project directory using the parameters returned by `generatePlatformTemplateParameters`:
  * Relative POSIX paths in `ExtensionPlatformTemplate.overwritePaths` must stay strictly within the project root (the host rejects absolute paths, `..` traversal segments, `.dart_tool/**`, and `pubspec.yaml`). Without `--overwrite`, an existing file listed in `overwritePaths` (for example, `'lib/main.dart'` when scaffolding a headless background service or multi-entrypoint application template) is overwritten only if its contents match the unmodified default `flutter create` skeleton; if the user has modified the file, the host preserves it and logs a status hint to pass `--overwrite`.
  * Package entries declared in `ExtensionPlatformTemplate.dependencies` (`packageName -> versionConstraint`) are merged under `dependencies:` in `pubspec.yaml` using insert-if-missing semantics (`!dependencies.containsKey(pkg) || overwrite`) prior to running `flutter pub get`.
* **Plugin Platform Stanza & `example/` App Scaffolding (`generatePluginPlatformConfig`)**: When scaffolding a plugin platform (`-t plugin` or `-t plugin_ffi`), `generatePluginPlatformConfig` receives `platform`, `templateType`, and `toolParameters` (including `templateFlags` and `templateOptions` so multi-language extensions such as Tizen C++ vs. C# plugins can emit the language-appropriate schema). If it returns a non-null map (for example, `{'pluginClass': '...', 'fileName': '...'}` or `{'ffiPlugin': true}`), the Flutter Tool merges that stanza under `flutter.plugin.platforms.<platform>` in the plugin's `pubspec.yaml`, inserting missing keys without overwriting existing user-edited keys unless `--overwrite` is passed to `flutter create`. In addition, because `<target_dir>/example` has its own `example/pubspec.yaml` that does not inherit `dev_dependencies` from the parent plugin when standalone, scaffolding a custom extension platform on `-t plugin` or `-t plugin_ffi` (whether via `--extension` or in-place `--platforms=<platform>`) copies the owning extension's dependency entry from `<target_dir>/pubspec.yaml` (or the enclosing Pub workspace root `pubspec.yaml`) into `example/pubspec.yaml` under `dev_dependencies` (skipping this copy when `example/` is a `resolution: workspace` member that already inherits the extension from the enclosing Pub workspace root `pubspec.yaml`; when copying a relative `path:` entry, the path is resolved from the declaring `pubspec.yaml`'s directory, `<target_dir>` or the workspace root, and rewritten relative to `example/`) and renders the extension's corresponding `.app` platform template into `example/` whenever that platform is also advertised in `TemplateService.appPlatforms`.
* **Add-to-App Module Targets (`flutter build <target>-module` & `BuildService.renderTemplate`)**: Following the Android (`.android/`) and iOS (`.ios/`) module pattern, `flutter create --template=module` remains platform-agnostic and does not require a separate module template hook on `TemplateService`. Instead, an extension's module `BuildTarget` (for example, `TizenModuleBuildTarget(this._buildService)` returned from `BuildService.buildTargets` for `flutter build tizen-module`, configured via `ExtensionOption`s such as `--output-dir` or `--tizen-language`) accepts its owning `BuildService` in its constructor and lazily scaffolds or refreshes its ephemeral host runner directory (such as `.tizen/`) during `BuildTarget.build` by invoking `_buildService.renderTemplate(...)` (`extension.renderTemplate` over the bidirectional `Peer`), while standard `BuildTarget`s that do not render templates remain `const`. This reuses the host tool's `.tmpl` / `.copy.tmpl` and path-placeholder Mustache engine without adding template-rendering dependencies to the extension package or exposing template rendering to non-build services.
* **Structured Scaffolding Hooks vs. Unified-Diff `.patch` Files**: Unified-diff `.patch` files against shared Flutter templates (used in SDK-pinned forks such as `flutter-tizen` via `git apply`) are intentionally omitted because context-line diffs break across Flutter SDK versions whenever upstream templates evolve and fail on user-modified `pubspec.yaml` or `.gitignore` files during additive `flutter create . --platforms=<platform>`. Every scenario previously handled with `.patch` files maps to structured, version-resilient hooks: extra pub dependencies (`multi-app/pubspec.yaml.patch`) use `ExtensionPlatformTemplate.dependencies`, plugin platform stanzas use `generatePluginPlatformConfig`, unmodified skeleton replacements (`lib/main.dart`) use `ExtensionPlatformTemplate.overwritePaths`, runner and ephemeral module ignore rules (`.gitignore.patch` and `module/.gitignore.patch`) live in self-contained `<platform>/.gitignore` files (or `*` inside `.<platform>/.gitignore` when generating an ephemeral module directory), and module language or output settings (`module/pubspec.yaml.patch`) are configured via `ExtensionOption`s on the module `BuildTarget`.

> [!NOTE]
> **Why standalone project templates (`flutter create -t <template>`) are not supported at this time**:
>
> * Under project-scoped `dev_dependencies` discovery (including two-stage `--extension` bootstrap), the base application or plugin skeleton already exists before the extension is resolved in `.dart_tool/package_config.json`, making a separate full-project creation template (`-t <custom>`) redundant or destructive (`--overwrite`).
> * In `flutter create`, `-t` (`--template`) selects the project *archetype* (`app`, `module`, `package`, `plugin`, `plugin_ffi`), whereas `--platforms` (and `ExtensionFlag` / `ExtensionOption` variants with `ExtensionPlatformTemplate.overwritePaths`) selects and customizes target platforms (`android`, `ios`, `linux`, `custom_embedder`, etc.); a custom embedder is a target platform rather than a new project archetype.
> * Both built-in Mustache variables and custom extension-computed Mustache variables (via `generatePlatformTemplateParameters`) are supported directly when rendering custom platform templates.
> * Because `TemplateService` is an `abstract base class`, support for standalone project templates can be added in a future release as a defaulted getter without breaking existing extensions if a workspace-level scaffolding use case arises.

```dart
/// Defines a platform application or bundle build pipeline exposed both as a
/// `flutter build <name>` CLI subcommand and as the programmatic build step
/// invoked by `flutter run`, `flutter drive`, `flutter test integration_test`,
/// and `flutter daemon` (`app.start`) via [TargetDevice.buildTarget].
@immutable
abstract base class BuildTarget {
  /// Configures a build target with its CLI help [description], [outputDir]
  /// template, and optional [shaderTargets], [targetOs], and
  /// [targetPlatforms].
  const BuildTarget({
    required this.description,
    required this.outputDir,
    this.shaderTargets,
    this.targetOs,
    this.targetPlatforms = const <String>{},
  });

  /// Subcommand name registered under `flutter build <name>`.
  String get name;

  /// Human-readable description shown in `flutter build --help`.
  final String description;

  /// Output directory template (supporting [BuiltInPlaceholders]) where build
  /// outputs are written.
  final String outputDir;

  /// Explicit set of shader targets to compile for this target during asset
  /// bundling, or `null` to derive defaults from [targetOs].
  final Set<ExtensionShaderTarget>? shaderTargets;

  /// Underlying operating system identifier for this target (such as `'linux'`
  /// for Linux-based custom embedders, or a custom OS identifier).
  final String? targetOs;

  /// Supported target platform identifiers for this build target, preserving
  /// insertion order.

  /// * When empty (`const <String>{}`), no `--target-platform` CLI option is
  ///   registered and [ExtensionBuildContext.targetPlatform] is `null`.
  /// * When containing a single platform, `targetPlatforms.single` is passed
  ///   automatically as [ExtensionBuildContext.targetPlatform] without adding a
  ///   redundant `--target-platform` CLI option.
  /// * When containing multiple platforms, `flutter build <name>` registers a
  ///   `--target-platform` CLI option defaulting to `targetPlatforms.first`.
  final Set<String> targetPlatforms;

  /// Custom boolean CLI flags registered on `flutter build <name>` and
  /// passed via [ExtensionBuildContext.buildFlags].
  List<ExtensionFlag> get flags => const <ExtensionFlag>[];

  /// Custom single-value CLI options registered on `flutter build <name>` and
  /// passed via [ExtensionBuildContext.buildOptions].
  List<ExtensionOption> get options => const <ExtensionOption>[];

/// The primary coordinator between the tool and extension compilation logic.
abstract base class BuildService extends ToolExtensionService {
  /// Platform application and bundle build pipelines provided by this extension
  /// (exposed as `flutter build <name>` subcommands and invoked by
  /// `flutter run`, `flutter drive`, `flutter test integration_test`, and
  /// `flutter daemon` via [TargetDevice.buildTarget]).
  List<BuildTarget> get buildTargets => const <BuildTarget>[];

  /// Fine-grained `flutter assemble` graph nodes provided by this extension.
  List<AssembleTarget> get assembleTargets => const <AssembleTarget>[];

  /// Maps `flutter.plugin.platforms.<key>` identifiers to project-relative
  /// runner directories (for example, `const <String, String>{'tizen': 'tizen'}`)
  /// for pre-build native plugin injection via [injectPlugins].
  Map<String, String> get pluginPlatformDirectories => const <String, String>{};

  /// Generates native plugin registrants, build-system inputs, or plugin
  /// symlinks inside [ExtensionPluginInjectionContext.runnerDirectory] during
  /// `flutter create`, `flutter pub get`, and pre-build tooling regeneration.
  Future<void> injectPlugins(ExtensionPluginInjectionContext context) async {}

  /// Renders an extension-bundled Mustache template directory ([templateUri], a
  /// `package:` URI within this extension package) into [destinationDirectory]
  /// (within the project root or build directory) via the host tool's template
  /// renderer over the bidirectional JSON-RPC `Peer`, returning the count of
  /// written files.
  ///
  /// Module [BuildTarget]s that lazily scaffold or refresh an ephemeral runner
  /// directory (such as `.tizen/`) accept their owning [BuildService] in their
  /// constructor (for example, `TizenModuleBuildTarget(this._buildService)`
  /// returned from [buildTargets]) and invoke `_buildService.renderTemplate`
  /// during [BuildTarget.build], whereas standard [BuildTarget]s without
  /// template rendering remain `const`.
  ///
  /// The host rejects `..` traversal segments, paths outside the extension
  /// package root or project/build directory, and calls made during
  /// [AssembleTarget.build] (which would write untracked files outside
  /// `flutter assemble`'s declared outputs).
  @nonVirtual
  Future<int> renderTemplate({
    required Uri destinationDirectory,
    required Uri templateUri,
    bool overwrite = true,
    Map<String, Object?> parameters = const <String, Object?>{},
  }) async {
    final Object? response = await sendHostRequest(
      ExtensionRpcMethods.renderTemplate,
      <String, Object?>{
        'destinationDirectory': destinationDirectory.toString(),
        'overwrite': overwrite,
        'parameters': parameters,
        'templateUri': templateUri.toString(),
      },
    );
    if (response case {'renderedFileCount': final int count}) {
      return count;
    }
    throw FormatException(
      'Expected {"renderedFileCount": int} from '
      '"${ExtensionRpcMethods.renderTemplate}", got ${response.runtimeType}.',
      response,
    );
  }
}
```

At build time, the tool requests the targets provided by the extension and integrates `AssembleTarget`s into its build dependency graph alongside built-in targets (`BuiltInTargets.kernelSnapshot`, `BuiltInTargets.copyAssets`, and `InstallCodeAssets`). `BuildTarget` serves as the single source of truth for `targetOs` and `shaderTargets`: when `BuildTarget` invokes `flutter assemble`, the host injects `targetOs` and `shaderTargets` into the `flutter assemble` environment defines (tracked in the build cache key) consumed by built-in targets (and standalone `flutter assemble` invocations can pass those defines explicitly). To keep target implementations simple, the tool handles dependency ordering, input and output validation (`ExtensionPatternSource`, `ExtensionArtifactSource`, `ExtensionHostArtifactSource`), and `.d` depfile tracking for incremental builds:

* **`BuiltInTargets.kernelSnapshot` (`targetOs`)**: When `BuildTarget.targetOs` matches one of the six Dart VM operating systems (`android`, `fuchsia`, `ios`, `linux`, `macos`, `windows`), the tool passes `--target-os <targetOs>` to `frontend_server` so AOT tree-shaking folds `Platform.isLinux` (and sibling OS getters) accurately; when `BuildTarget.targetOs` is `null` or a custom/RTOS identifier (such as `'freertos'`), the tool omits `--target-os` so `Platform.operatingSystem` evaluates at runtime while still linking the platform kernel.
* **`BuiltInTargets.copyAssets` (`ShaderCompiler` & `shaderTargets`)**: Compiles shaders for each target in `BuildTarget.shaderTargets`, deriving defaults from `BuildTarget.targetOs` when `shaderTargets` is `null` (`'linux'`, `'android'`, and `'windows'` default to `{.sksl, .gles, .gles3, .vulkan}`; `'macos'` defaults to `{.sksl, .metal}`; `'ios'` defaults to `{.metal}`; `'fuchsia'` defaults to `{.sksl, .vulkan}`; and when `BuildTarget.targetOs` is `null` or an unrecognized/custom identifier, `shaderTargets` defaults to `{.sksl}`, matching `ShaderCompiler`'s existing fallback, while custom C/C++ embedders using OpenGL ES or Vulkan either set `targetOs: 'linux'` or declare `shaderTargets` explicitly, such as `const <ExtensionShaderTarget>{.sksl, .gles, .vulkan}`).
* **Code Size Analysis (`--analyze-size`, `bundleDirectoryUri`, & `aotSnapshotFileName`)**: When `--analyze-size` (or `--code-size-directory`) is passed to `flutter build <name>`, the host populates `ExtensionBuildContext.codeSizeDirectory` (and forwards `CodeSizeDirectory` into `flutter assemble`) so the extension's `gen_snapshot` invocation writes `snapshot.<targetPlatform>.json` and `trace.<targetPlatform>.json` into `codeSizeDirectory`. Host `SizeAnalyzer.analyzeAotSnapshot` execution is gated strictly on `codeSizeDirectory != null && result.bundleDirectoryUri != null`: when both are non-null, `ExtensionBuildSubCommand` verifies that `snapshot.<targetPlatform>.json` and `trace.<targetPlatform>.json` exist in `codeSizeDirectory` (exiting with an actionable error if `bundleDirectoryUri` is returned under `--analyze-size` without those V8 snapshot profile and trace JSON files), locates `result.aotSnapshotFileName` (defaulting to `'libapp.so'`) inside `result.bundleDirectoryUri`, writes `~/.flutter-devtools/<targetPlatform>-code-size-analysis_*.json`, and prints the size breakdown summary.

When constructing `ExtensionAssembleContext.extraDefines` for `AssembleTarget.build`, the tool filters out reserved built-in `flutter assemble` environment keys (`BuildMode`, `TargetPlatform`, `TargetFile`, `DartDefines`, `BuildName`, `BuildNumber`, `Flavor`, `TreeShakeIcons`, `DartObfuscation`, `SplitDebugInfo`, `TrackWidgetCreation`, `CodeSizeDirectory`, `ExtraFrontEndOptions`, `ExtraGenSnapshotOptions`, `DeferredComponents`), which are already surfaced as typed fields on `ExtensionBuildContext`, so `extraDefines` contains only custom `-dKey=Value` defines. Intermediate `AssembleTarget`s pass generated data to downstream targets via files in `ExtensionAssembleContext.buildDir` declared in `outputs` rather than mutating `Environment.defines` mid-build, preserving `Environment.defines` immutability and build-directory cache hash stability across incremental builds.

Before starting a build, the tool verifies that all required artifacts are available (downloading missing custom artifacts via `ArtifactService` if needed) and populates `ExtensionBuildContext.resolvedArtifacts`. Artifact resolution is scoped to the **owning extension** rather than merging all installed extensions' artifacts into a single flat map, and built-in engine artifacts (`BuiltInArtifacts`) always take precedence over custom extension artifacts on key collision, both when resolving `ExtensionArtifactSource` inputs and when populating `resolvedArtifacts`. For target-specific built-in engine artifacts (such as `genSnapshot`), if `artifact.platform` is omitted and `AssembleTarget.targetPlatform` holds a custom platform identifier, the tool requires an explicit built-in `platform` rather than silently defaulting to `android-arm`, and fails fast if a single target declares conflicting `(platform, mode)` requests that resolve to different paths for the same artifact name.

1. **Custom Platform Flutter Plugins (`ExtensionPlugin` & `BuildService.injectPlugins`)**:
   * When a plugin's `pubspec.yaml` declares an embedder platform entry under `flutter.plugin.platforms.<platformKey>` (with `pluginClass`, `dartPluginClass`, `ffiPlugin`, or custom platform keys), the Flutter Tool parses non-built-in keys and resolves matching plugins for both pre-build native runner tooling and build-time bundle packaging:
     * **Dart-only plugin implementations (`dartPluginClass`)**: Universally supported across arbitrary platforms. The tool registers the implementation in `.dart_tool/flutter_build/dart_plugin_registrant.dart` guarded by the compile-time environment define `const String.fromEnvironment('FLUTTER_CUSTOM_PLATFORM') == '<platformKey>'` (rather than checking `Platform.operatingSystem` at runtime, which would misidentify a custom Linux-based embedder as desktop Linux or fail on an unknown OS).
     * **Pre-build native plugin injection (`BuildService.pluginPlatformDirectories` & `BuildService.injectPlugins`)**: First-party desktop platforms (`linux/`, `windows/`, `macos/`) generate `generated_plugin_registrant.*`, CMake/plugin build inputs, and `.plugin_symlinks/` during `flutter create`, `flutter pub get`, and `FlutterCommand`'s pre-build `regeneratePlatformSpecificTooling` step so native runner projects open cleanly in external IDEs (such as Visual Studio, CLion, or Tizen Studio) immediately after `flutter pub add` and work when invoking `flutter assemble` directly. For each entry `<platformKey>: <runnerDir>` in `BuildService.pluginPlatformDirectories`, those same host hooks invoke `BuildService.injectPlugins` **only when `<projectRoot>/<runnerDir>` exists on disk and `(extensionDillStamp, .flutter-plugins-dependencies, releaseMode)` differs from `.dart_tool/flutter_build/extension_plugins.stamp`**, keeping warm CLI invocations with unchanged plugins free of extra isolate spawns.
     * **Build-time native plugin metadata (`ExtensionBuildContext.plugins`)**: The tool also passes the resolved `List<ExtensionPlugin>` metadata (`name`, `path`, and the parsed `configuration` map from `flutter.plugin.platforms.<platformKey>`, filtered by `BuildTarget.pluginPlatformKey`) to `BuildTarget.build` and `AssembleTarget.build` via `ExtensionBuildContext.plugins`. Providing the parsed `configuration` map (including `pluginClass`, `dartPluginClass`, `ffiPlugin`, and custom per-plugin manifest keys such as required system permissions, privileges, or entitlements) avoids re-parsing plugin `pubspec.yaml` files during bundle packaging while leaving native build-system integration (CMake, GN, Meson, MSBuild, or Make) in the extension's control.
2. **Dart Hooks (`package:hooks` / `package:code_assets`) for FFI Native Assets**:
   * `BuildTarget` exposes `Future<ExtensionNativeAssetsConfig?> resolveNativeAssetsConfig(ExtensionBuildContext context)`, which receives the active `ExtensionBuildContext` so multi-architecture targets (`targetPlatforms`) and targets with custom toolchain `ExtensionOption`s or `configuration` can compute `targetArchitecture`, `targetOs`, and compiler paths per build invocation using `context.targetPlatform`, `context.buildOptions`, `context.configuration`, and `context.resolvedArtifacts`. Note that `ExtensionNativeAssetsConfig.targetOs` may intentionally differ from `BuildTarget.targetOs` because `package:code_assets` requires one of its six known OS values whereas `BuildTarget.targetOs` may be a custom OS identifier or `null`. When an `AssembleTarget` depends on `install_code_assets` (`InstallCodeAssets`), the tool passes the resolved `ExtensionNativeAssetsConfig` into the hooks runner, compiling and bundling `CodeAsset`s into `native_assets/<targetOs>/`.
   * **POSIX Toolchain Constraint (`CCompilerConfig`)**: Because `package:code_assets`'s `CCompilerConfig` on POSIX hosts currently accepts only bare executable `Uri`s (`ar`, `cc`, `ld`) without per-invocation flag arrays, cross-toolchains that require `--sysroot` or target ABI flags must supply wrapper executables at those `Uri`s until upstream `package:code_assets` (`dart-lang/native`) adds native sysroot and compiler flag fields.
   * **Arbitrary OS Caveat**: Dart's `package:code_assets` (`OS` in `package:code_assets/code_assets.dart`) currently requires target OS identifiers from a fixed set of known operating systems (`android`, `fuchsia`, `iOS`, `linux`, `macOS`, `windows`). Consequently, Dart Hooks work out of the box for custom embedders that target one of these underlying OS kernels (such as embedded Linux distributions using `targetOs: 'linux'` with a custom cross-compiler toolchain), whereas arbitrary custom operating systems (such as an RTOS or a proprietary embedded OS) cannot use `package:code_assets` hooks without upstream Dart SDK / `package:code_assets` support or OS mapping.
   * **Why Wire & Diagnostic Models Live in `package:flutter_tools_core` Rather Than Re-Exporting `package:code_assets` / `package:hooks`**:
     * **Dependency Footprint & Application `pub` Solve Isolation**: Because extensions are declared in the consuming application's `pubspec.yaml`, every dependency of `package:flutter_tools_core` and `package:flutter_tools_extension` participates in the application's `pub` version solve. Keeping `package:flutter_tools_core` pure Dart (`package:collection` and `package:meta` only, with zero `dart:io` or `dart:ffi` imports) avoids pulling `hooks`, `code_assets`, `record_use`, `yaml`, `crypto`, `logging`, and `pub_semver` into application solves and decouples `package:flutter_tools_core`'s semantic versioning from `hooks` and `code_assets` major version bumps.
     * **Host-Mediated Hook Execution & Wire Serialization**: Extension isolates do not invoke `hooks_runner` directly; instead, host `flutter_tools` translates `ExtensionNativeAssetsConfig` through `flutter assemble` defines into the Flutter SDK's bundled `hooks_runner` (and `CCompilerConfig` in `package:code_assets` lacks a `const` constructor and public JSON wire serialization). Adding new toolchain fields in `package:code_assets` therefore requires coordinated host plumbing in `flutter_tools` regardless of whether `CCompilerConfig` were re-exported.
     * **Diagnostic Model Alignment (`ValidationResult` vs. `hook/doctor.dart`)**: Host `package:flutter_tools` already depends on `package:hooks` and can map hook diagnostic results into `ValidationResult` and `ValidationMessage` (see [Section 4.2](#42-diagnostics-flutter-doctor)) on the host side without adding dependencies to `package:flutter_tools_core`. If `dart doctor`, `package:hooks`, and `flutter doctor` unify on a shared diagnostic model in the future, those pure-Dart classes (`ValidationResult`, `ValidationMessage`, `ValidationType`, and `ValidationMessageType`) can live in a zero-dependency leaf package re-exported by both `package:hooks` and `package:flutter_tools_core`.

Host integration with `DeviceService` follows these contracts:

* **Application Identity & Package Resolution (`resolveApplication`)**:
  * **When invoked**: Before running `flutter run`, `flutter install`, `flutter drive`, or `flutter test integration_test -d <device>` against an extension-backed device, the host resolves a device-scoped `ApplicationPackage` (via `ApplicationPackageFactory.getPackageForDevice`) by invoking `DeviceService.resolveApplication` with `ExtensionApplicationResolutionContext(buildMode: ..., deviceId: device.id, project: project.toExtensionProject(), applicationBinaryUri: ..., flavor: ...)`.
  * **Why `DeviceService`**: `resolveApplication` lives on `DeviceService` rather than `BuildTarget` because `TargetDevice.buildTarget` is optional, resolution is keyed by `deviceId`, and prebuilt archives (`--use-application-binary`) may be resolved or inspected without invoking a build target. Because `DeviceService` and `BuildService` run in the same extension isolate, extensions with a `BuildTarget` can share their bundle output path helper between `BuildTarget.build` and `DeviceService.resolveApplication` so `flutter install` never drifts from `flutter build`.
  * **Return value & fallback**: When `resolveApplication` returns an `ExtensionApplicationPackage`, the host constructs an `ApplicationPackage` with `id` set to `appId` (for example, `'com.example.my_app'` from `webos/appinfo.json`, `tizen-manifest.xml`, or a prebuilt archive) and `bundleUri` set to the returned `bundleUri`. If `resolveApplication` returns `null` or fails with JSON-RPC `-32601` (`METHOD_NOT_FOUND` on an older extension), the host falls back to an `ApplicationPackage` using the project's `pubspec.yaml` `name` as `id` and `applicationBinaryUri` as `bundleUri`. Whenever `applicationBinaryUri` (`--use-application-binary`) is supplied, the resolved host package implements `PrebuiltApplicationPackage`.
* **Launching, Attaching & End-to-End Testing (`flutter run`, `flutter attach`, `flutter drive`, `flutter test integration_test -d <device>`)**:
  * **Build vs. prebuilt launch (`launchApp`)**: `startApp` on extension-backed devices requires a non-null `ApplicationPackage` (throwing a `StateError` if `package` is `null`). When `package` implements `PrebuiltApplicationPackage` (`--use-application-binary`), the host skips `BuildTarget.build` and calls `DeviceService.launchApp` with `appId: package.id`, `executableUri: package.bundleUri`, `prebuiltApplication: true`, and `ExtensionDebuggingOptions`. Otherwise, the host invokes the associated `BuildTarget.build` (passing `targetDeviceId: device.id` and the absolute entrypoint `mainPath`, which may be a temporary generated test runner outside `projectRoot` during `flutter test integration_test -d <device>`) and calls `launchApp` with `appId: package.id`, `executableUri` set to `ExtensionBuildResult.executableUri`, and `prebuiltApplication: false`.
  * **Engine switches & hot reload**: Within `ExtensionDebuggingOptions`, `engineSwitches` is authoritative for the Flutter engine command line, while `route` and `deviceVmServicePort` are provided as typed hints for platform launchers and port forwarders. During `flutter run` and `flutter attach`, the host resolves `targetOs`, `shaderTargets`, and `pluginPlatformKey` from `TargetDevice.buildTarget` to configure shader hot reload and pass `-DFLUTTER_CUSTOM_PLATFORM=<pluginPlatformKey>` to `ResidentCompiler`.
  * **VM Service discovery & port forwarding (`getVmServiceUri`)**: Rather than exposing a separate port-forwarding interface across the isolate boundary, port forwarding is encapsulated inside `DeviceService`. After `launchApp` (during `flutter run`, `flutter drive`, and `flutter test integration_test -d <device>`, passing `appId: package.id`) or directly during `flutter attach` (passing `--app-id` if specified, or `appId: null` to target the active or most recently launched Flutter application on the device), the host calls `getVmServiceUri(deviceId: device.id, appId: ..., deviceVmServicePort: ..., hostVmServicePort: ...)`. For remote targets, the extension discovers the device VM Service, establishes the host-to-device tunnel, and returns the local HTTP VM Service URI (`http://127.0.0.1:<hostPort>/<authToken>=/`) for the resident runner and Dart Development Service (DDS).
* **Installation Lifecycle & Error Handling (`supportsInstall`, `installApp`, `uninstallApp`, `isAppInstalled`)**:
  * **Capability gating (`TargetDevice.supportsInstall`)**: `installApp`, `uninstallApp`, and `isAppInstalled` are gated together by `TargetDevice.supportsInstall`. When `supportsInstall` is `false`, the host makes no installation RPCs and returns no-op results (`isAppInstalled` returns `false`, `uninstallApp` returns `true` so `flutter drive` teardown succeeds quietly, and standalone `flutter install` is rejected). When `supportsInstall` is `true`, the extension must implement all three methods.
  * **Standalone `flutter install`**: Never triggers a build. When `--uninstall-only` is passed, the host checks `isAppInstalled(appId: app.id, deviceId: device.id)` and, if installed, calls `uninstallApp(appId: app.id, deviceId: device.id)`. Otherwise, when `--use-application-binary` is omitted, the host first verifies that `app.bundleUri` is non-null and exists on disk (failing with an actionable error instructing the user to run `flutter build <buildTarget>` first or pass `--use-application-binary` if missing). For both prebuilt (`app is PrebuiltApplicationPackage`) and built-bundle installs, the host then checks `isAppInstalled(appId: app.id, deviceId: device.id)`, calls `uninstallApp(appId: app.id, deviceId: device.id)` if the app is already installed, and calls `installApp(bundleUri: app.bundleUri, deviceId: device.id, prebuiltApplication: app is PrebuiltApplicationPackage)`.
  * **Operational errors**: Any JSON-RPC error from `launchApp`, `stopApp`, `installApp`, `uninstallApp`, or `isAppInstalled` on a device where the operation is invoked (including `-32001` `ToolExtensionException` and `-32002` `UnsupportedError`) is logged via `logger.printError` and treated as an operational failure (`LaunchResult.failed()` or `false`).
* **Emulator Management (`getEmulators`, `launchEmulator`, `createEmulator`)**: `flutter emulators` aggregates emulator descriptors from `DeviceService.getEmulators`, and `flutter emulators --launch <id> [--cold]` delegates to `DeviceService.launchEmulator`. For emulator creation (`flutter emulators --create [--name <name>] [--platform <platform>]`), `flutter emulators` adds an optional `--platform <platform>` option (`android` or an extension platform identifier). When `--platform` is passed, the host routes `--create` directly to that provider; when `--platform` is omitted, the host delegates directly if only one emulator-creation provider (Android `avdmanager` or a single active extension implementing `createEmulator`) is available, prompts the user via `promptForOption` in interactive terminals when multiple providers are available, or fails with an actionable error listing the available `--platform` options in non-interactive environments. Extensions return the created `TargetEmulator` on success, throw `UnsupportedError` (JSON-RPC `-32002`) when emulator creation is unsupported, and throw `ToolExtensionException` (JSON-RPC `-32001`) on operational failure, matching `launchEmulator`.
* **Log Streaming (`startLogStream`, `stopLogStream`, `device.logEntry`)**: Each extension-backed device uses a single host log reader that starts streaming via `DeviceService.startLogStream(deviceId: device.id, appId: app?.id)` (passing the resolved `app.id` during `flutter run` and `flutter drive`, or `appId: null` during device-wide `flutter logs`), receives lines from `device.logEntry` notifications matching `deviceId`, and stops streaming via `stopLogStream(deviceId: device.id)`.
* **Daemon Serialization (`flutter daemon`)**: The `flutter daemon` wire schema is unchanged (requiring no `540-ide` protocol additions): `device.added` populates the existing open-string `platform` field with `TargetDevice.targetPlatform` (matching `flutter custom-devices`, which IDE clients already handle as an open string), and `device.forward` and `device.unforward` return a structured daemon error on extension-backed devices because port forwarding is encapsulated inside `DeviceService`. Daemon `ProxiedDevice` binary transfer (`device.uploadApplicationPackage`, which keys solely on built-in `TargetPlatform` names without a `deviceId`) is not supported for extension-backed devices.
* **Teardown (`stopApp` & `shutdown`)**: When the user quits (`q`) or a test run completes, the host invokes `DeviceService.stopApp(deviceId: device.id, appId: app?.id)` to terminate the specified application (or the active/most recently launched application when `appId` is `null`) and close its tunnel; when the user detaches (`d`) or exits the CLI, `DeviceService.shutdown()` tears down any active tunnels and log reader subprocesses.

#### 4.8 Artifacts (`flutter precache`)

Extensions requiring custom artifacts (i.e., custom engine binaries, sysroots, or cross-compilation toolchains for different host and target architectures) provide an implementation of `ArtifactService`, which declares the `ArtifactDependency` items required for a given Flutter engine version and `HostPlatform`.

```dart
  /// [url] when omitted (`ArchiveFormat.zip` when [url]'s path ends with
  /// `.zip` case-insensitively, or `ArchiveFormat.none` otherwise).

    required this.sha256,
    required this.url,

  final String sha256;

  final Uri url;

  /// Whether this artifact is a `.zip` archive extracted into a directory.
```

Each `ArtifactDependency` is either a `RemoteArtifactDependency` (`ArtifactDependency.remote`) or a `LocalArtifactDependency` (`ArtifactDependency.local`):

* **Remote Artifacts (`ArtifactDependency.remote` / `RemoteArtifactDependency`)**: Require an `http` or `https` `url` and a 64-character hex `sha256` digest alongside `name` and optional `archiveFormat` (defaulting to `ArchiveFormat.zip` when `url` ends with `.zip`) for cryptographic integrity verification. The Flutter Tool downloads and extracts these artifacts into a content-addressed cache under `$DART_DATA_HOME/flutter_tool_extensions/artifacts/<extensionName>/<sha256>/<name>`, using cross-process file locking and atomic directory renames. On POSIX hosts, the host `ArtifactService` runner marks downloaded `ArchiveFormat.none` files executable (`chmod +x`) when `RemoteArtifactDependency.isExecutable` is `true`, and for extracted `.zip` archives (`ArchiveFormat.zip`) validates that every entry in `RemoteArtifactDependency.executables` is a relative in-tree POSIX path within the extracted directory (rejecting `'.'`, `'..'`, absolute paths, and symlinks) before setting executable permissions (`chmod +x`) alongside any Unix executable mode bits preserved in archive metadata. Keying the cache by SHA-256 ensures that unchanged cross-compilers or sysroots are not re-downloaded when the Flutter engine revision advances, and prevents two projects using different versions of an extension from overwriting each other's cached binaries. Running `flutter precache --force` re-verifies and refreshes cached extension artifacts.
* **Local Artifact Overrides (`ArtifactDependency.local` / `LocalArtifactDependency`)**: Strictly intended for developer local-engine overrides (returned by `ArtifactService.listRequiredArtifacts` only when an extension's `ConfigOption` or environment variable points to a local build, and never hardcoded in published extensions). `ArtifactDependency.local` resolves a local directory or file `file:` `Uri` without requiring a static `sha256`. When a `LocalArtifactDependency` is referenced via `ExtensionArtifactSource` in `flutter assemble`, the tool tracks `stampUri` for directory overrides (or the file's modification timestamp when `localUri` is a file) rather than hashing an entire local engine `out/` directory tree on every build, ensuring that rebuilding the local engine invalidates downstream assemble targets cleanly.

#### 4.9 Project Cleanup (`flutter clean`)

Because custom build systems may write intermediate outputs outside the standard `build/` directory, extensions can implement `CleanService` to clean up project-local state when `flutter clean` is invoked. 1. **Hermetic In-Process Unit Tests (`ServiceTestHarness`)**:
   * Extension authors instantiate `*Service`, `BuildTarget`, and `AssembleTarget` classes directly in the test isolate (injecting standard ecosystem fakes such as `package:file`'s `MemoryFileSystem` or `package:process` when testing I/O, avoiding `Isolate.spawn` heap-copying). Wrapping a `ToolExtensionService` in `ServiceTestHarness` (`addTearDown(harness.dispose)`) wires in-memory notification capture (`logs`, `deviceLogLines`, and custom notifications) and host-callback stubs (for `getConfigurationValues`, `promptForOption`, `promptForInput`, and `BuildService.renderTemplate`) while exercising `service.shutdown()` on `dispose()`.
2. **Package Entrypoint & Capability Conformance (`verifyExtensionPackage`)**:
   * `await verifyExtensionPackage(packageRoot: Uri.directory('.'))` verifies `extension/flutter_tools/extension.dart` exists inside `packageRoot`, spawns it via `Isolate.spawnUri` over a real `IsolateChannel` and JSON-RPC 2.0 `Peer`, validates `ToolExtensionCapabilities` (`services` and `supportedHostPlatforms`, skipping service RPCs when the current host is excluded), checks `BuildTarget` and `AssembleTarget` name uniqueness (with name validity enforced by `ExtensionBuildTarget.fromJson` / `ExtensionAssembleTarget.fromJson`), verifies static `package:` template directory existence via `Isolate.resolvePackageUri`, and sends `extension.shutdown` without leaking `ReceivePort`s.

```dart
// test/custom_embedder_extension_test.dart
import 'package:flutter_tools_extension/flutter_tools_extension.dart';
import 'package:flutter_tools_extension/testing.dart';
import 'package:test/test.dart';

import '../extension/flutter_tools/extension.dart';

void main() {
  test('hermetic build target unit test', () async {
    const target = CustomEmbedderBuildTarget();
    final Uri projectRoot = Uri.parse('file:///workspace/app/');
    final Uri outputDir = projectRoot.resolve('build/custom_embedder/release/');

    final ExtensionBuildResult result = await target.build(
      ExtensionBuildContext(
        buildMode: .release,
        flutterRoot: Uri.parse('file:///sdk/flutter/'),
        mainPath: '/workspace/app/lib/main.dart',
        outputDir: outputDir,
        projectRoot: projectRoot,
        resolvedArtifacts: const <String, String>{},
        trackWidgetCreation: false,
        treeShakeIcons: true,
      ),
    );

    expect(result.executableUri, outputDir.resolve('bundle/'));
  });

  test('captures device logs and notifications in-process', () async {
    final deviceService = CustomEmbedderDeviceService();
    final harness = ServiceTestHarness<CustomEmbedderDeviceService>(deviceService);
    addTearDown(harness.dispose);

    final List<TargetDevice> devices = await deviceService.getDevices();
    expect(devices, hasLength(1));
    expect(devices.single.id, 'embedder-01');

    deviceService.emitLogLine(deviceId: 'embedder-01', line: 'booted');
    expect(harness.deviceLogLines('embedder-01'), <String>['booted']);
  });

  test('verifies extension entrypoint and capabilities', () async {
    await verifyExtensionPackage(packageRoot: Uri.directory('.'));
  });
}
```

On the host side within `packages/flutter_tools/test/`, unit and integration tests verify device-aware `ApplicationPackageFactory` resolution (`DeviceService.resolveApplication` with `ExtensionApplicationResolutionContext`, its `null` / `-32601` fallback to the project's `pubspec.yaml` `name`, and `PrebuiltApplicationPackage` wrapping for `--use-application-binary`), `TargetDevice.supportsInstall` gating for `installApp` / `uninstallApp` / `isAppInstalled`, standalone `flutter install` (prior build output verification, `--use-application-binary`, and `--uninstall-only`), `flutter drive` and `flutter test integration_test -d <device>` (including external temporary `mainPath` entrypoints), and `startLogStream` `appId` filtering.

## Performance Characteristics & Benchmarking

Because extension discovery runs across daily `flutter` CLI and IDE daemon invocations, startup work is structured across four execution paths:

1. **Zero-Extension Projects**: Reading direct `(dev_)dependencies` from `pubspec.yaml`, resolving their `rootUri` entries in `.dart_tool/package_config.json`, and checking `File.existsSync()` on `<rootUri>/extension/flutter_tools/extension.dart` performs only local filesystem stat checks and spawns zero subprocesses or isolates.
2. **Cold `.dill` Snapshot Compilation**: On first invocation (or after `package_config.json`, a transitive `.d` source file, or the Flutter/Dart SDK revision stamp changes), the tool compiles `extension/flutter_tools/extension.dart` to `<workspace>/.dart_tool/flutter_tools/extensions/<package>/extension.dill` via `dart compile kernel` (~0.8s on Linux for the reference prototype extension) and persists `ToolExtensionCapabilities` in `extension.dill.stamp`.
3. **Warm Capability-Skipped Invocations**: When an installed extension does not register the service required by the current command (for example, a device-only extension during `flutter clean`) or excludes the current `HostPlatform` in `supportedHostPlatforms`, the host reads cached capabilities from `extension.dill.stamp`, verifies `.d` modification timestamps on disk, and skips `Isolate.spawnUri` completely.
4. **Warm Active-RPC Invocations**: Commands that invoke active extension services spawn precompiled `.dill` isolates in-process via `Isolate.spawnUri` and `Peer.withoutJson` (sharing the running Dart VM without OS process startup or UTF-8 JSON serialization overhead) and query multiple active extensions concurrently with `Future.wait`.

Today, only `dev/devicelab/lib/tasks/flutter_tool_startup.dart` exists (tracking warm CLI startup on standard zero-extension projects); dedicated startup benchmark coverage for projects with active tool extensions (covering cold `.dill` compilation, warm capability-skipped invocations, and warm active-RPC invocations such as `flutter devices --machine` and `flutter doctor`) will be added before enabling `--enable-tool-extensions` by default.

## Alternatives Considered

### 1. Forking `flutter_tools` or Maintaining Wrapper CLIs

* **Description**: Embedder teams maintain separate CLI wrappers (such as `flutter-elinux` or `flutter-tizen`) that invoke `flutter assemble` internally or fork `packages/flutter_tools`.
* **Why Rejected**: Wrapper CLIs break standard IDE integrations (VS Code and IntelliJ/Android Studio invoke `flutter daemon` and `flutter run`), duplicate command-line flag parsing, and require constant rebasing as internal `flutter_tools` classes evolve.

### 2. Extending `flutter custom-devices` JSON Configuration

* **Description**: Expand the declarative JSON schema in `custom_devices.json` with additional shell command hooks for builds and templates.
* **Why Rejected**: Complex build graphs (`AssembleTarget`), incremental depfiles, Dart Hooks (`package:code_assets`) cross-compilation, structured `flutter doctor` validation, and multi-step device protocols cannot be expressed reliably or portably as flat shell command strings in a static JSON file.

### 3. Global Machine-Wide Extension Registry (`flutter extensions` CLI)

* **Description**: An early iteration of this design proposed a global registry (`extension_registry.json`) managed via `flutter extensions install/uninstall` commands, or recompiling `flutter_tools.snapshot` with extension packages baked in.
* **Why Rejected**: Global installation breaks project reproducibility across developer machines and CI environments, causes version conflicts when local projects target different versions of the same embedder SDK, creates ambiguity when multiple globally installed extensions register overlapping platform or option names, and still does not populate IDE "New Project" dialogs (since VS Code and IntelliJ/Android Studio currently hardcode the six built-in platforms in IDE UI code). Baking third-party extensions into `flutter_tools.snapshot` also risks breaking the entire Flutter SDK installation if an extension fails to compile. Project-scoped `dev_dependencies` in `pubspec.yaml`, paired with `flutter create --extension=<package>` for single-command bootstrap, ensure that both initial project creation and `git clone` followed by `flutter pub get` reproduce the exact target tooling required by the workspace.

### 4. Separate Package Resolution (Dart 3.10+ Analyzer Plugin Model) vs. `dev_dependencies`

* **Description**: Dart 3.10+ analyzer plugins moved out of `dev_dependencies` into an `analysis_options.yaml` `plugins:` section with a dedicated background `pub` solve so analyzer plugin dependencies never constrain the application's own package solve.
* **Trade-offs**: Discovering tool extensions via `dev_dependencies` and `extension/flutter_tools/extension.dart` (the DevTools `extension/<target_package>/` directory convention) avoids a second `.dart_tool/` solve during `flutter pub get`, keeps `package:flutter_tools_extension`'s dependencies minimal (`flutter_tools_core`, `json_rpc_2`, `stream_channel`, `meta`, and `collection`, keeping `package:flutter_tools_extension` free of `test_api` to avoid version-solve conflicts with `flutter_test`'s pinned `test_api` constraint), and integrates directly with existing pub workspaces.

### 5. Out-of-Process `stdio` Subprocesses vs. Dart Isolates (`Isolate.spawnUri`)

* **Description**: Spawn each extension as a separate OS process (`dart run <entrypoint>.dill`) communicating with the Flutter Tool over `stdin`/`stdout` JSON-RPC 2.0 pipes instead of `Isolate.spawnUri`.
* **Trade-offs**: A separate OS process provides full OS-level isolation (`stdout`, `exit()`, `Directory.current`, and FFI crashes cannot affect the Flutter Tool) and decouples the extension's execution mode from the host runtime. Conversely, `Isolate.spawnUri` shares the already-running Dart VM (spawning `.dill` kernel snapshots when the tool runs in JIT mode, or `.aot` snapshots if the tool is compiled with `dart compile exe`), avoiding separate VM startup latency and UTF-8 JSON serialization overhead (`Peer.withoutJson` passes Dart maps directly across `SendPort`). Because the wire protocol is already standard JSON-RPC 2.0 over a `StreamChannel`, the transport layer can add or switch to a `stdio` `StreamChannel` with zero changes to the seven service contracts if process-level sandboxing is required in the future.

### 6. Static YAML Manifest (`extension/flutter_tools/config.yaml`) or `hook/flutter_tool_extension.dart` vs. `extension/flutter_tools/extension.dart`

* **Description**: Discover extensions either via `package:extension_discovery` and a static `extension/flutter_tools/config.yaml` manifest (with a `bin/<package_name>.dart` entrypoint) or via a `hook/flutter_tool_extension.dart` entrypoint.
* **Trade-offs**:
  1. *Against `extension/flutter_tools/config.yaml` (`package:extension_discovery`) + `bin/<package_name>.dart`*: Duplicating services, host platforms, build targets, and template platforms in YAML creates drift hazards and lacks dartdoc or type checking, and once capability registration lives in typed Dart on `ToolExtensionEntryPoint.run` (cached alongside the platform-independent `.dill` snapshot after the first handshake), `config.yaml` degenerates to `{}` (where a 0-byte file silently parses as `null` in `package:extension_discovery`). Furthermore, `extension_discovery`'s `.dart_tool/extension_discovery/` cache optimizes scanning all transitive packages in `package_config.json` (which `flutter_tools` discards when filtering to direct `pubspec.yaml` dependencies) while hardcoding `dart:io` instead of `package:file`, `pub.dev` (`pana`) does not inspect `extension/<target>/config.yaml` (`dependency:flutter_tools_extension` works out of the box), and placing an isolate `SendPort` script in `bin/` causes `pub.dev` (`pana`) to falsely tag the package `has:executable`.
  2. *Against `hook/flutter_tool_extension.dart`*: In the Dart ecosystem, `hook/*.dart` (`package:hooks_runner`) is an SDK-agnostic convention (shared across `dart` and `flutter` builds) for package-scoped lifecycle hooks executed transitively across every package in the dependency graph as short-lived standalone CLI processes (`void main(List<String> args)` reading `--config=<input.json>`). By contrast, `extension/<target_package>/` scopes extensions to a specific SDK tool (`extension/flutter_tools/extension.dart`, `extension/devtools/`), restricts discovery to direct project dependencies, and spawns long-lived JSON-RPC isolates (`Future<void> main(List<String> args, Object? message)` receiving a `SendPort`).

## Open Questions

1. **Extension Namespace & Identifier Collisions**:
   * How should the Flutter Tool handle collisions when two installed extensions declare the same `BuildTarget.name`, `TemplateService` platform identifier, or `TargetDevice.id`, or when a third-party extension declares a target name that collides with a built-in platform (such as `linux` or `apk`)?
   * *Proposed Resolution*: Built-in platform names, CLI flags and options, build subcommands, and engine artifacts always take precedence over third-party extensions (emitting a visible warning naming the offending extension package and skipping the colliding registration), and collisions between two active extensions resolve deterministically in lexicographical `<package_name>` order (keeping the first extension's registration, emitting a visible warning naming both packages, and skipping the duplicate).
2. **Crash Reporting & Analytics Attribution**:
   * When an extension isolate throws an unhandled exception or returns an `RpcException`, how should the Flutter Tool attribute the failure in telemetry and crash reporting so defects in third-party extension packages do not pollute first-party crash buckets or leak third-party local file paths?
   * *Proposed Resolution*: Catch and wrap extension RPC and isolate-exit failures in a distinct host-side exception (using JSON-RPC error code `-32001` for intentional `ToolExtensionException` domain errors and `-32000` for unhandled extension crashes) that is excluded from first-party `flutter_tools` crash reporting.
3. **Protocol Versioning, Backwards Compatibility & Breaking Changes**:
   * Because extension packages are published independently to `pub.dev` while `flutter_tools` ships with the user's Flutter SDK, how should the JSON-RPC wire protocol evolve over time without breaking existing extensions or older Flutter SDKs, and what governance process should apply to breaking changes?
   * *Design Exploration*:
     * **Protocol Capability Negotiation & Graceful Degradation**: Include an explicit `protocolVersion` (and optional per-service feature capabilities) in the `extension.getCapabilities` handshake response. When the tool encounters an extension speaking an older minor protocol version, it can gracefully skip newer optional RPCs or fall back to default behavior; when an extension requires a minimum protocol version newer than the host tool, the tool can surface a clear diagnostic instructing the user to upgrade Flutter or pin a compatible extension version.
     * **Additive Evolution of RPCs, Parameters & Wire Models**: Because all service classes are `abstract base class`, new service methods can be added with safe default implementations (for example, returning an empty collection or throwing `UnsupportedError` mapped to `-32002`). On the wire, data models in `package:flutter_tools_core` ignore unknown JSON map keys during deserialization and provide sensible defaults for newly introduced optional fields:
       * *Incoming RPCs with new parameters will not break older extensions*: Because JSON-RPC 2.0 `params` is a named `Map<String, Object?>` and extensions are compiled against their own `pub.dev`-resolved version of `package:flutter_tools_extension`, when a newer Flutter Tool sends additional RPC parameters on the wire, an extension compiled against an older version of `package:flutter_tools_extension` simply ignores the unknown parameter keys during deserialization and invokes its existing service method without breaking.
       * *Dart API evolution via semantic versioning*: At the Dart API level, adding a new parameter directly to an abstract or overridden service method signature (or changing existing parameter types) is a standard semantic-versioning breaking change in `package:flutter_tools_extension` (requiring a major version bump on `pub.dev`), whereas adding new defaulted fields to existing context/parameter classes (`ExtensionBuildContext`, `ExtensionAssembleContext`, `ExtensionDebuggingOptions`, `ExtensionApplicationResolutionContext`, `ExtensionFlutterProject`, `CleanEnvironment`) or new defaulted methods on `abstract base class` services is non-breaking. Direct abstract-method signature changes are therefore landed during pre-1.0 (`0.x`) stabilization; once `package:flutter_tools_extension` reaches `1.0.0`, abstract method signatures are frozen within each major version and new inputs are added via context objects or defaulted methods. Because the wire protocol remains backwards-compatible, bumping the major version of `package:flutter_tools_extension` does not break already-published extensions on newer Flutter SDKs; extension authors only encounter the Dart signature change when they opt into upgrading their `package:flutter_tools_extension` constraint.
     * **Deprecation Windows & Breaking Change Policy**: Establish a formal deprecation policy for wire protocol changes between `flutter_tools` and `pub.dev`-published extensions: deprecate superseded RPC methods or fields in `package:flutter_tools_extension` while maintaining host-side support across a defined number of stable Flutter releases (matching Flutter's breaking change policy), accompanied by migration guides and conformance checks in `verifyExtensionPackage`.
4. **Shared Artifact Cache Eviction**:
   * How should stale content-addressed `<sha256>` artifact directories in `$DART_DATA_HOME/flutter_tool_extensions/artifacts/` be garbage-collected over time (for example, via LRU timestamp pruning during `flutter precache` or an explicit `flutter clean --extensions-cache` flag)?

## Appendix: Usage Examples

### A.1 Implementing a Custom Embedder Extension

An embedder maintainer creates a Dart package (e.g., `package:flutter_custom_tools`), implements the relevant services from `package:flutter_tools_extension`, and exposes the conventional `extension/flutter_tools/extension.dart` isolate entrypoint.

```dart
// extension/flutter_tools/extension.dart
import 'package:flutter_tools_extension/flutter_tools_extension.dart';

/// Builds a Flutter application bundle for the custom embedder target.
final class CustomEmbedderBuildTarget extends BuildTarget {
  const CustomEmbedderBuildTarget()
    : super(
        description: 'Build a custom embedder bundle.',
        outputDir:
            '${BuiltInPlaceholders.outputDir}/custom_embedder/${BuiltInPlaceholders.buildMode}',
        targetOs: 'linux',
        targetPlatforms: const <String>{'custom-arm64', 'custom-x64'},
      );

  /// The subcommand name registered under `flutter build`.
  @override
  String get name => 'custom-embedder';

  /// Compiles and packages the application bundle inside
  /// [ExtensionBuildContext.outputDir].
  @override
  Future<ExtensionBuildResult> build(ExtensionBuildContext context) async {
    final Uri bundleDir = context.outputDir.resolve('bundle/');
    return ExtensionBuildResult(executableUri: bundleDir);
  }
}

/// Exposes custom embedder build targets to the Flutter Tool.
final class CustomEmbedderBuildService extends BuildService {
  /// High-level `flutter build` targets provided by this extension.
  @override
  List<BuildTarget> get buildTargets => const <BuildTarget>[
    CustomEmbedderBuildTarget(),
  ];
}

/// Discovers and manages connected custom embedder hardware.
final class CustomEmbedderDeviceService extends DeviceService {
  /// Queries device tooling or scans the network for target hardware.
  @override
  Future<List<TargetDevice>> getDevices() async {
    return const <TargetDevice>[
      TargetDevice(
        buildTarget: 'custom-embedder',
        category: Category.other,
        ephemeral: true,
        id: 'embedder-01',
        name: 'Custom Embedder Reference Board',
        sdkNameAndVersion: 'CustomOS 2.1',
        supportsInstall: false,
        supportsScreenshot: false,
        supportsScreenRecording: false,
        targetPlatform: 'custom-arm64',
      ),
    ];
  }

  /// Checks whether [project] contains a `custom_embedder/` runner directory.
  @override
  Future<bool> isSupportedForProject({
    required String deviceId,
    required ExtensionFlutterProject project,
  }) async {
    return true;
  }

  /// Installs and launches [executableUri] on [deviceId] and forwards the
  /// VM Service port to the host machine.
  @override
  Future<void> launchApp({
    required String appId,
    required ExtensionDebuggingOptions debuggingOptions,
    required String deviceId,
    required Uri executableUri,
    bool prebuiltApplication = false,
  }) async {}

  /// Returns the host-forwarded HTTP VM Service URI for hot reload and
  /// DevTools.
  @override
  Future<Uri?> getVmServiceUri({
    required String deviceId,
    String? appId,
    int? deviceVmServicePort,
    int? hostVmServicePort,
  }) async {
    return Uri.parse('http://127.0.0.1:41235/abcd1234efgh=/');
  }

  /// Terminates the running application and tears down port forwarding.
  @override
  Future<void> stopApp({required String deviceId, String? appId}) async {}
}

/// Adds `--platforms=custom_embedder` support to `flutter create`.
final class CustomEmbedderTemplateService extends TemplateService {
  /// Maps the `custom_embedder` platform identifier to its template directory.
  @override
  Map<String, String> get appPlatformTemplates => const <String, String>{
    'custom_embedder':
        'package:flutter_custom_tools/templates/custom_embedder',
  };
}

/// Isolate entrypoint spawned by the Flutter Tool via `Isolate.spawnUri`.
Future<void> main(List<String> args, Object? message) async {
  await ToolExtensionEntryPoint.run(
    message,
    <ToolExtensionService>[
      CustomEmbedderBuildService(),
      CustomEmbedderDeviceService(),
      CustomEmbedderTemplateService(),
    ],
    supportedHostPlatforms: <HostPlatform>{
      .darwin_arm64,
      .darwin_x64,
      .linux_arm64,
      .linux_x64,
    },
  );
}
```

### A.2 CLI Workflow for App Developers

Once the extension is published to `pub.dev` or available locally in a workspace, application developers use standard `flutter` CLI commands:

```sh
# 1. Enable the experimental tool extensions feature flag.
$ flutter config --enable-tool-extensions

# 2. Create a new Flutter project, add the embedder extension to
#    dev_dependencies, and scaffold its custom platform runner in one step
#    (to add the extension and platform to an existing project instead, run
#    `flutter create . --extension=flutter_custom_tools`).
$ flutter create --extension=flutter_custom_tools my_embedded_app
$ cd my_embedded_app

# 3. Verify environment readiness and connected target hardware.
$ flutter doctor
$ flutter devices

# 4. Run with hot reload, build a release bundle, and clean build outputs.
$ flutter run -d embedder-01
$ flutter build custom-embedder --release
$ flutter clean
```
