# RFC 710.0000: Style guide changes for package private

## Overview

This document proposes updating the [Flutter repository style guide](https://github.com/flutter/flutter/blob/main/docs/contributing/Style-guide-for-Flutter-repo.md) and [Flutter breaking change policy](https://github.com/flutter/flutter/blob/main/docs/contributing/Tree-hygiene.md#handling-breaking-changes) to adopt `@internal` for package-private APIs across `flutter/flutter` and `flutter/packages`.

Declarations in `lib/src/` that are not exported by public barrel files (`lib/<layer>.dart`) and are marked `@internal` fall outside the public API contract; modifying or removing them is not a breaking change.

## Context

The style guide discourages package-private APIs beyond library-private (`_`) declarations and requires every file in `lib/src/<layer>/` to be exported by `lib/<layer>.dart`. When an implementation detail is needed across multiple files within a layer, contributors are left with two poor options:

* Keep declarations library-private (`_`), which forces all related code into a single large file (or requires `part`/`part of`, which exposes every `_` declaration across all part files and removes file-level encapsulation).
* Expose implementation details as public APIs (such as `FocusAttachment` or `FocusTraversalPolicy.invalidateScopeData`), which commits the framework to backward compatibility and discourages refactoring.

In practice, the framework already omits `_`-prefixed files in `lib/src/` from barrel exports (such as `lib/src/widgets/_accessibility_evaluations.dart`, `lib/src/widgets/_window.dart`, and `lib/src/foundation/_features.dart`), and `flutter/packages` already uses `@internal` with `hide` (such as `GoRouterStateRegistry` in `go_router`).

Relying on filename conventions alone risks accidental leaks. Because `lib/src/` files are re-exported by default, moving code or sharing a non-private class within a layer can inadvertently expose it to external consumers, making future edits breaking changes. Marking these declarations `@internal` triggers an [`invalid_export_of_internal_element`](https://dart.dev/tools/diagnostics/invalid_export_of_internal_element) analyzer error if exported from a public barrel file, and triggers [`invalid_use_of_internal_member`](https://dart.dev/tools/diagnostics/invalid_use_of_internal_member) if external consumers import `lib/src/` directly.

## Proposal

### Breaking change policy and customer tests

* Modifying, renaming, or removing any declaration in `lib/src/` that is not exported by a public barrel file and is annotated with `@internal` is not a breaking change and requires no deprecation period or announcement.
* Registered tests in [`flutter/tests`](https://github.com/flutter/tests) must not import `package:flutter/src/` or depend on `@internal` APIs. Breakages in customer tests caused by `package:flutter/src/` imports or `@internal` usage are not breaking changes, and contributors may disable or update offending customer tests when modifying `@internal` declarations.

### Package-private APIs (`@internal`)

Use `@internal` from `package:meta` when an implementation detail is shared across files within the same layer (`lib/src/<layer>/`) or accessed by framework unit tests in `packages/flutter/test/`.

#### Relationship to `@visibleForTesting` and feature flags

* `@internal` is for package-private declarations omitted or hidden from public barrel exports.
* `@visibleForTesting` remains discouraged on public declarations (except when combined with `@protected`), because declarations exported by a public barrel file remain reachable by external consumers without importing `lib/src/`.

#### Placement rules

* `@internal` may be applied to top-level declarations and to `static` members or constructors of public classes inside `lib/src/`.
* In any file in `lib/src/` not exported by a barrel file, all public top-level declarations must be annotated with `@internal` (excluding conditional-import implementation files such as `_*_io.dart` and `_*_web.dart`).
* `@internal` must not be applied to an instance member of a public class unless both:
  * The enclosing class has the `base`, `final`, or `sealed` modifier so external packages cannot `implement` it (preferring `final` or `sealed`, since adding a new member to a `base` class can still collide with a member in an external subclass).
  * The instance member is annotated with `@nonVirtual` so subclasses cannot override it.

#### Barrel exports and file naming

* Drop the requirement that every file in `lib/src/<layer>/` be exported by `lib/<layer>.dart` (superseding [flutter/flutter#108632](https://github.com/flutter/flutter/issues/108632)).
* Any file in `lib/src/<layer>/` not exported by `lib/<layer>.dart` must have a `_` filename prefix (such as `lib/src/widgets/_accessibility_evaluations.dart`), and have all public top-level declarations annotated with `@internal`.
* When an `@internal` top-level declaration shares a file with public declarations, `lib/<layer>.dart` must exclude it with `hide` (such as `export 'src/widgets/foo.dart' hide InternalBar;`). Omitting `hide` in `lib/<layer>.dart` triggers [`invalid_export_of_internal_element`](https://dart.dev/tools/diagnostics/invalid_export_of_internal_element). (`hide` is not required on intra-`src/` re-exports.)
* Cross-layer imports in `lib/src/` must continue importing top-level barrel files (`package:flutter/<layer>.dart`) rather than another layer's `lib/src/` files, with `lib/src/foundation/_features.dart` as the only permitted exception for framework-wide feature flags.

#### Enforcement

* Accidental public exports of `@internal` declarations are caught by the analyzer's [`invalid_export_of_internal_element`](https://dart.dev/tools/diagnostics/invalid_export_of_internal_element) diagnostic, and external usage is caught by [`invalid_use_of_internal_member`](https://dart.dev/tools/diagnostics/invalid_use_of_internal_member) and `implementation_imports`.
* Repository-specific rules (requiring unexported `lib/src/` files to use a `_` prefix and annotate public top-level declarations with `@internal`, and enforcing instance-member placement rules) will be enforced via custom analyzer lint rules.
