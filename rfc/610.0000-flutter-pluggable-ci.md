# RFC 610.0000: Flutter Pluggable CI Design

## 1. Problem Statement

To allow partners who maintain off-tree embedders to detect regression immediately after a commit lands on the flutter main branch by running their CI on every flutter PR post-submit.

## 2. Background

Multiple Flutter partners adopt custom embedders to support specific platforms not officially supported by Flutter. Changes in the upstream Flutter repository often cause build failures for custom embedders. Depending on how frequently a partner syncs their fork, isolating the exact breaking change is difficult to manage. This solution mitigates the issue by allowing partners to run their CI pipelines against every Flutter PR post-submit, catching regressions early. We cannot allow partner CI execution to block the tree, at least for now, because gardeners responsible for maintaining tree health lack the knowledge or access to partner codebases and infrastructure necessary to resolve failures effectively.

### 2.1. Audience

* Flutter TLs
* First-party partners

### 2.2. Glossary

* **In-Tree Platforms:** These are core Flutter platforms that are stored, updated, and managed directly inside the main Flutter repository. This includes the official ports for iOS, Android, macOS, Linux, Windows and Web.
* **Out-of-Tree Platforms:** These are external Flutter platforms developed and maintained by third parties in separate, independent repositories. Because they live outside the main codebase, today developers must fork the Flutter tool and reverse-engineer undocumented system channels (like text input or app lifecycles) to make them work.
* **Custom Embedders:** These are platform-specific codebases that host the Flutter engine and Dart runtime on non-standard operating systems. They act as out-of-tree ports for custom hardware.
* **Cocoon:** Flutter's custom Continuous Integration (CI) orchestration system that integrates underlying CI services like LUCI with GitHub to schedule tests and report build statuses. It also provides developer tooling such as auto-submit mechanisms, test flakiness tracking, and powers the public Flutter Pre-submit/Build Dashboards.
* **LUCI (Layered Universal Continuous Integration):** The underlying execution engine that runs Flutter's testing and build workloads across diverse platforms like macOS, Windows, and Linux. Orchestrated by Cocoon, LUCI executes specific Python-based "recipes" to securely validate code changes for the Flutter framework, engine, and packages during both pre-submit and post-submit pipelines.

## 3. Overview

To enable Flutter to scale across external platforms and out-of-tree embedder maintainers, Flutter infrastructure (Cocoon) requires a robust, secure, and decoupled communication model. This system notifies partner CI pipelines of post-submit commits on `flutter/flutter` so partners can execute custom test suites on proprietary hardware and report execution status back to the Flutter build dashboard.

Key architectural goals include non-blocking test execution, strict security via [Ed25519](https://www.rfc-editor.org/info/rfc8410/) public/private key authentication, high resilience against network outages, and minimal operational overhead for Flutter infrastructure maintainers.

The proposed solution is to use webhooks for bidirectional asynchronous communication backed internally by GCP Pub/Sub for fault tolerance and retries.

Below is a high-level flow diagram of the proposed communication between Cocoon and Partner CI:

### 3.1 Non-goals

This design does not cover what kind of CI for out-of-tree platforms to use and what tests to run to validate custom embedders. Nor does it cover how to guarantee the delivery of CI execution status from partner CI systems back to Cocoon.

## 4. Detailed Design

Integration with third-party CIs requires two main points of discussion: communication and authentication. For external system notification, the recommended approach is a bi-directional webhook server-to-server communication, combined with a manual on-demand status reconciliation mechanism.

### 4.1. Primary Design: Webhook Server-to-Server Communication (Push-Callback) with Manual Status Request

In this architecture, Cocoon uses standard HTTP webhooks to push event notifications to external partner endpoints. External partners process the event asynchronously on their custom infrastructure and send execution status back via Cocoon's callback REST API. Additionally, partners must host an endpoint capable of responding to on-demand status queries from Cocoon to enable manual status checks from the build dashboard, eliminating automated polling loops.

#### 4.1.1. End-to-End Workflow Diagram

##### 4.1.1.1. Internal processing of post submit event

1. GitHub notifies Cocoon via `/api/github/webhook-subscription` when a PR with `sha=wxyz` merged.
2. Cocoon schedules tasks on LUCI and creates records in `tasks` collection in Firestore for each configured partner.
3. For every configured partner, Cocoon:
   * Creates a record in Firestore with a `uid` (unique ID) to map partner notifications to Cocoon tasks,
   * Publishes a message containing the `uid` and commit context (`sha`, `pr`, `slug`, etc.) to an internal GCP Pub/Sub topic.

```mermaid
sequenceDiagram
    participant PubSub@{"type":"queue"}
    actor GitHub as GitHub Repo
    participant Cocoon as Cocoon Server
    participant Firestore@{"type":"database"}
    destroy GitHub
    GitHub->>+Cocoon: Postsubmit Event
    Cocoon->>Firestore: Creates record in `tasks` collection<br/>for sha=wxyz with uid=abcd,<br/> partner name, attempt number, etc.
    Cocoon->>-PubSub: Schedule partner notification<br/>event for sha=wxyz with uid=abcd
```

##### 4.1.1.2. Cocoon calls partner webhook to notify about post submit to run CI, retrying on failures

1. A Pub/Sub subscriber:
   * receives partner notification event,
   * fetches partner configurations,
   * generates a short-lived JWT signed with an [Ed25519](https://www.rfc-editor.org/info/rfc8410/) private key,
   * issues an HTTP POST webhook request to the partner's configured URL.
2. If webhook invocation times out or partner server returns 5xx (Server error) or 408 (Request Timeout) response, Cocoon will not acknowledge the Pub/Sub message and will retry the dispatch.
3. If a partner webhook responds with success code 200 or client error code 4xx (except 408 Request Timeout), Cocoon will log that as an error. Status code 409 (Conflict) will be considered an already processed notification and will be logged as a warning. In both cases, Cocoon will acknowledge the message and will not retry the dispatch.

```mermaid
sequenceDiagram
    participant PubSub@{"type":"queue"}
    participant Cocoon as Cocoon Server
    participant Partner as Partner CI

    PubSub->>+Cocoon: Receive partner notification<br/>event for sha=wxyz with uid=abcd
    Cocoon->>+Partner: HTTP POST (signed with cocoon key,<br/>JWT body with notification for sha=wxyz with uid=abcd)
    Partner->>Cocoon: HTTP GET to Cocoon JWKS url if missed in cache
    Cocoon-->>Partner: JWKS to verify JWT signature
    Note over Partner: Internal Failure during processing the request
    Partner-->>-Cocoon: Response 500
    Cocoon-->>-PubSub: nack

    PubSub->>+Cocoon: Retry partner notification<br/>event for sha=wxyz with uid=abcd
    Cocoon->>+Partner: Retry HTTP POST (signed with cocoon key,<br/>JWT body with notification for sha=wxyz with uid=abcd)
    Partner->>Cocoon: HTTP GET to Cocoon JWKS url if missed in cache
    Cocoon-->>Partner: JWKS to verify JWT signature
    Partner-->>Cocoon: Response 200
    Cocoon-->>-PubSub: ack
    Note over Partner: Start executing custom tests
```

##### 4.1.1.3. Optionally, Partner may notify cocoon it started test execution and provide test details

1. When the partner CI begins test execution for `sha=wxyz` (`uid=abcd`), it may send a signed JWT callback to Cocoon with `in_progress` status along with scheduled test names and links to execution details.
2. Cocoon verifies the JWT signature (fetching the partner's JWKS on cache miss), publishes the status to Pub/Sub, responds with `200`, and updates the task status in Firestore to `in_progress`.
3. That will lead to showing test names and links to execution details in the Cocoon build dashboard.

```mermaid
sequenceDiagram
    participant PubSub@{"type":"queue"}
    participant Cocoon as Cocoon Server
    participant Partner as Partner CI

    Partner->>+Cocoon: HTTP POST Callback (signed with partner key, JWT body<br/>with `in_progress` status for sha=wxyz with uid=abcd)
    Cocoon->>Partner: HTTP GET to Partner JWKS url if missed in cache
    Partner-->>Cocoon: JWKS to verify JWT signature
    Cocoon->>PubSub: Partner test execution status<br/>for sha=wxyz with uid=abcd
    Cocoon-->>-Partner: Response 200

    PubSub->>+Cocoon: Partner test execution status<br/>for sha=wxyz with uid=abcd
    Note over Cocoon: Update Partner task status to `in_progress`. If provided,<br/>display scheduled test names and links to execution details.
    deactivate Cocoon
```

##### 4.1.1.4. Optionally, if supported by Partner, Cocoon can poll for status updates

Partners may host a status endpoint (e.g., `GET /status?uid=abcd`).

1. In the event that a webhook callback fails to arrive or a build hangs, authorized users can manually trigger a status query from the Cocoon build dashboard while waiting for execution results.
2. Cocoon will make a GET request to the partner's status endpoint, fetch the latest status, and update the task state accordingly.

**Note:** Automated polling is strictly rejected to avoid DoS risks and operational overhead.

```mermaid
sequenceDiagram
    participant Cocoon as Cocoon Server
    participant Partner as Partner CI

    Note over Cocoon: User requested task status while waiting execution results
    Cocoon->>Partner: HTTP GET /status?uid=abcd
    Partner-->>Cocoon: Response 202 {"status": "in_progress"}

    Note over Partner: Continue executing custom tests
```

##### 4.1.1.5. Partner calls cocoon webhook to provide CI run status update, retrying on failures

1. Once the partner CI finishes executing tests on proprietary hardware for `sha=wxyz` (`uid=abcd`), it makes an HTTP POST callback to Cocoon signed with the partner's key containing the terminal execution status (`cancelled`, `infra_failure`, `failed`, `succeeded`, `neutral`, `skipped`), summary message, and test URLs.
    * If the callback request experiences a response timeout or receives a retryable failure response (`5xx` or `408 Request Timeout`), the partner CI retries the HTTP POST callback for `uid=abcd`.
    * Upon receiving the callback, Cocoon reads the Key ID (`kid`) from the JWT header and looks up the corresponding cached public key. If the public key is not found in cache, it fetches the partner's JWKS to update the cache, or responds with `401` if the key is not found or JWT signature validation fails.
    * If Cocoon successfully validates the payload and publishes the partner test execution status to Pub/Sub, it responds with status code `200`.
    * If Cocoon fails to process the request, it responds with non-retryable error status code, such as `400` for a validation error, `404` if the `uid` is not found, `409` if already processed, or `413` if the body size exceeds 8MB.
2. Once Cocoon receives the partner test execution status for `sha=wxyz` (`uid=abcd`) from Pub/Sub, it updates the partner task state in Firestore.

```mermaid
sequenceDiagram
    participant PubSub@{"type":"queue"}
    participant Cocoon as Cocoon Server
    participant Partner as Partner CI

    Note over Partner: Finishes executing custom tests
    Partner->>Cocoon: HTTP POST Callback (signed with partner key,<br/>JWT body with status for sha=wxyz with uid=abcd)
    Note over Partner: Response timeout

    Partner->>+Cocoon: Retry HTTP POST (signed with partner key,<br/>JWT body with status for sha=wxyz with uid=abcd)
    Cocoon->>Partner: HTTP GET to Partner JWKS url if missed in cache
    Partner-->>Cocoon: JWKS to verify JWT signature
    Cocoon->>PubSub: Partner test execution status<br/>for sha=wxyz with uid=abcd
    Cocoon-->>-Partner: Response 200

    PubSub->>+Cocoon: Partner test execution status<br/>for sha=wxyz with uid=abcd
    Note over Cocoon: Update Partner task status for sha=wxyz with uid=abcd
    deactivate Cocoon
```

##### 4.1.1.6. If test failed, Cocon may request re-run of failed task

1. When a task re-run is initiated for commit `sha=wxyz` (either automatically by Cocoon's flake/retry policy or manually from the build dashboard), Cocoon generates a new unique correlation ID (`uid=efgh`) for the new attempt while retaining the original commit `sha=wxyz`, and publishes a new dispatch message to Pub/Sub.
2. The Pub/Sub subscriber sends a new signed JWT HTTP POST notification to the Partner CI webhook containing `sha=wxyz` and `uid=efgh`. Issuing a distinct `uid` ensures the partner treats the request as a new execution rather than rejecting it as a duplicate (`409 Conflict`) of `uid=abcd`.
3. The Partner CI verifies the new JWT signature, re-executes the custom tests for `sha=wxyz`, and sends a signed JWT callback to Cocoon reporting the updated status (e.g., `succeeded`) associated with `uid=efgh`.
4. Cocoon verifies the callback signature, processes the status update through Pub/Sub, and updates the task status in Firestore to `succeeded` for `sha=wxyz` (`uid=efgh`).

```mermaid
sequenceDiagram
    participant PubSub@{"type":"queue"}
    participant Cocoon as Cocoon Server
    participant Partner as Partner CI

    opt Cocoon calls partner webhook to re-run failed task
        Cocoon->>+Cocoon: Re-run for uid=efgh requested
        Cocoon->>PubSub: Schedule partner notification<br/>event for sha=wxyz with uid=efgh
        PubSub->>Cocoon: Receive partner notification<br/>event for sha=wxyz with uid=efgh
        Cocoon->>+Partner: HTTP POST (signed with cocoon key,<br/>JWT body with notification for sha=wxyz with uid=efgh)
        Partner->>Cocoon: HTTP GET to Cocoon JWKS url if missed in cache
        Cocoon-->>Partner: JWKS to verify JWT signature
        Partner-->>Cocoon: Response 200
        Cocoon-->>-PubSub: ack
    end

    Note over Partner: Executing custom tests

    opt Partner calls cocoon webhook to provide CI run status update
        Partner->>+Cocoon: HTTP POST Callback (signed with partner key,<br/>JWT body with status for sha=wxyz with uid=efgh)
        Partner-->>Cocoon: JWKS to verify JWT signature
        Cocoon->>PubSub: Partner test execution status<br/>for sha=wxyz with uid=efgh
        Cocoon-->>-Partner: Response 200
        deactivate Partner

        PubSub->>+Cocoon: Partner test execution status<br/>for sha=wxyz with uid=efgh
        Note over Cocoon: Update Partner task status for sha=wxyz with uid=efgh
        deactivate Cocoon
    end
```

#### 4.1.2. Security & Authentication

This section details the decentralized security model used to authorize server-to-server bidirectional webhook communication without a centralized authorization server.

##### 4.1.2.1. Asymmetric Cryptography & Key Management

Both the Cocoon server and the Partner CI server independently generate their own asymmetric key pairs (using [Ed25519](https://www.rfc-editor.org/info/rfc8410/)). Each system stores its private key in a secure key management system and shares its corresponding public key with the other party.

By leveraging decentralized asymmetric cryptography, this approach intentionally avoids the need for a central Authorization Server or Identity Provider, eliminating a potential single point of failure and reducing infrastructure complexity.

##### 4.1.2.2. Key Distribution Strategy: Public Key Endpoints

For this authentication model to work, both parties must reliably obtain public keys. Each system exposes a dedicated, unauthenticated public JWKS endpoint. See [RFC 7517: JSON Web Key (JWK)](https://www.rfc-editor.org/info/rfc7517) for details of JWKS format. This endpoint serves the public key(s) and key ID(s) (`kid`). Both parties configure their systems to fetch or refresh this key periodically. This is highly secure because it allows Cocoon and Partners to rotate their keys seamlessly without manual intervention.

Example of JWKS: <https://firebaseappcheck.googleapis.com/v1/jwks>

##### 4.1.2.3. Serialized JWT HTTP Body

When either system sends an HTTP request (Cocoon dispatching a webhook or a Partner sending status callbacks), the sender constructs a POST request as follows:

* **Header**: `Content-Type: application/jwt`
* **Body**: A signed JSON Web Token (JWT)

##### 4.1.2.4. JWT Payload Structure

The JWT consists of a base64 encoded header, payload, and signature separated by dots.
For example:

`eyJhbGciOiJFZERTQSIsInR5cCI6IkpXVCIsImtpZCI6MTIzNDV9.eyJpc3MiOiJjb2Nvb24iLCJhdWQiOiJodHRwczovLzNwLXBhcnRuZXItY2kuY29tIiwiaWF0IjoxNzc0OTYyMDAwLCJleHAiOjE3NzQ5NjIzMDAsImRhdGEiOnsic2x1ZyI6ImZsdXR0ZXIvZmx1dHRlciIsInByIjoxMjM0NSwic2hhIjoiNmYwZjFjMmQzZTRmNWE2YjdjOGQ5ZTBmMWEyYjNjNGQ1ZTZmN2E4YiJ9fQ.GnIgnoVR7LeMbs4we6Q39Aw7S7f994Ng_TJomRuROoqiN3HUd8o5BqwSzoeo94jkHYpTuAdCxO60fx6G69zVCA`

##### 4.1.2.5. JWT Header

```json
{
  "alg": "EdDSA",
  "typ": "JWT",
  "kid": "12345"
}
```

Where:

* **alg**: The cryptographic algorithm used to sign the token (e.g., `EdDSA` for [Ed25519](https://www.rfc-editor.org/info/rfc8410/) signatures).
* **typ**: The type of the token, which is set to `JWT`.
* **kid**: Key ID that identifies the specific public key needed to verify the token's signature from the JWKS endpoint.

##### 4.1.2.6. JWT Payload

```jsonc
{
  // --- Standard Security Metadata ---
  "iss": "cocoon",
  "aud": "https://3p-partner-ci.com/webhook",
  "iat": 1774962000,
  "exp": 1774962300,
  // --- The Actual Message (Custom Claims) ---
  "data": {
    "slug": "flutter/flutter",
    "pr": 12345,
    "sha": "6f0f1c2d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8b"
  }
}
```

##### 4.1.2.7. JWT Signature

[Ed25519 signature](https://www.rfc-editor.org/info/rfc8037/#appendix-A.4) as defined in [RFC 8037](https://www.rfc-editor.org/info/rfc8037).

##### 4.1.2.8. Validating Incoming Requests

Webhook listeners validate incoming requests in accordance with standard JWT/JWS/JWKS specifications and security best practices, specifically:

* [RFC 7519 Section 7.2](https://www.rfc-editor.org/info/rfc7519/#section-7.2) for JWT validation;
* [RFC 7515 Section 5.2](https://www.rfc-editor.org/info/rfc7515/#section-5.2) for signature verification;
* [RFC 7517 Section 4.5](https://www.rfc-editor.org/info/rfc7517/#section-4.5) & [Section 5](https://www.rfc-editor.org/info/rfc7517/#section-5) for `kid` lookup via cached JWKS;
* [RFC 8725 Section 3](https://www.rfc-editor.org/info/rfc8725/#section-3) for algorithm pinning and `iss`/`aud`/`exp` claim checks.

In addition, Cocoon's callback endpoint validates that `data.uid` exists, has not been processed yet and belongs to a partner that is listed in `iss` claim.

#### 4.1.3. Pros & Cons

* **Pros:**
  * Industry-standard webhook architecture that is easy for partners to consume.
  * Push-based trigger is real-time and minimizes latency.
  * Decouples Flutter core infrastructure from partner device management.
  * Stateless design on Cocoon via Firestore/Redis and GCP Pub/Sub.
  * Status query endpoints allow robust reconciliation on-demand without automated polling loops.
* **Cons:**
  * Requires partners to maintain publicly accessible HTTP endpoints and handle inbound requests.

### 4.2. Alternatives Considered

#### 4.2.1. Event-Driven GCP Pub/Sub Integration (Asynchronous Event Bus)

This architecture eliminates direct server-to-server HTTP calls by leveraging Google Cloud Pub/Sub as an event bus between Cocoon and partner infrastructure.

##### 4.2.1.1. End-to-End Workflow Diagram

```mermaid
sequenceDiagram
    actor GitHub as GitHub Repo
    participant Cocoon as Cocoon Server
    participant PubSub@{"type":"queue"}
    participant Partner as Partner CI

    destroy GitHub
    GitHub->>Cocoon: Postsubmit Event
    Note over Cocoon: Creates Partner task
    Cocoon->>PubSub: Publish Event
    PubSub->>Partner: Partner Ingestion (JWT+Service Account)
    Note over Partner: Executes custom tests
    Partner->>PubSub: Publish Results (JWT+Service Account)
    PubSub->>Cocoon: Update Partner task status
    Note over Cocoon: Update Partner task status
```

##### 4.2.1.2. Workflow

* **1. Trigger:** GitHub triggers post-commit processing in Cocoon.
* **2. Outbound Event:** Cocoon schedules the partner task and publishes an event to an outbound Pub/Sub topic.
* **3. Partner Ingestion:** Partners consume messages from the topic via cross-project GCP IAM subscription or delegation.
* **4. Execution:** Partner CI processes the event on local hardware.
* **5. Inbound Result:** Partner CI publishes results directly back to Cocoon's inbound Pub/Sub topic.
* **6. Dashboard Update:** Cocoon ingests result messages and updates test execution states in the dashboard.

##### 4.2.1.3. Pros & Cons

* **Pros:**
  * Highly asynchronous and resilient; messages are automatically buffered during outages.
  * No inbound HTTP ports are required on the partner side; can run behind strict firewalls.
  * Removes webhook management, network connection timeouts, and custom HTTP retry logic.
* **Cons:**
  * High administration overhead: requires managing cross-project GCP permissions or GCP service account keys for partners.
  * Introduces cloud vendor lock-in (GCP) for third-party partners.
  * Increases setup and development complexity for partners.
  * Cannot validate message body at the time of message submission.

#### 4.2.2. Alternative 2: Automated Polling Strategy (Push Trigger, Pull Status)

This hybrid model retains HTTP push for triggering partner CI jobs, but replaces inbound callbacks with periodic polling by Cocoon to check test completion.

##### 4.2.2.1. End-to-End Workflow Diagram

```mermaid
sequenceDiagram
    participant PubSub@{"type":"queue"}
    actor GitHub as GitHub Repo
    participant Cocoon as Cocoon Server
    participant Partner as Partner CI
    destroy GitHub

    GitHub->>Cocoon: Postsubmit Event
    Note over Cocoon: Creates Partner task
    Cocoon->>PubSub: Schedule partner notification<br/>event for sha=wxyz with uid=abcd
    PubSub->>Cocoon: Receive partner notification<br/>event for sha=wxyz with uid=abcd
    Cocoon->>Partner: HTTP POST (signed with cocoon key,<br/>JWT body with notification for uid=abcd)
    Partner-->>Cocoon: Response 200
    Cocoon-->>PubSub: ack
    Cocoon->>PubSub: Schedule pull partner CI status event<br/>for sha=wxyz with uid=abcd

    loop Polling by using PubSub retry
        PubSub->>Cocoon: Receive pull partner CI status event<br/>for sha=wxyz with uid=abcd
        Note over Partner: Executes custom tests
        Cocoon->>Partner: GET /status?uid=abcd
        Partner-->>Cocoon: Response 202, Status: RUNNING
        Cocoon-->>PubSub: nack
    end

    PubSub->>Cocoon: Receive pull partner CI status event<br/>for sha=wxyz with uid=abcd
    Cocoon->>Partner: GET /status?uid=abcd
    Partner-->>Cocoon: Response 200, Status: COMPLETED
    Cocoon-->>PubSub: ack
    Cocoon->>PubSub: Schedule Partner test execution status<br/>for sha=wxyz with uid=abcd
    PubSub->>Cocoon: Receive Partner test execution status<br/>for sha=wxyz with uid=abcd
    Note over Cocoon: Update Partner task status
    Cocoon-->>PubSub: ack
```

##### 4.2.2.2. Workflow

* **1. Trigger & Dispatch:** GitHub triggers Cocoon, which creates partner tasks and pushes a webhook notification to the partner.
* **2. Execution:** The partner CI executes workloads asynchronously.
* **3. Polling Loop:** Cocoon automatically queries the partner's status endpoint periodically (e.g., using Pub/Sub retry loop).
* **4. Inbound Processing:** Once the status endpoint returns a terminal state (`PASSED`/`FAILED`), Cocoon updates the dashboard.

##### 4.2.2.3. Pros & Cons

* **Pros:**
  * Prevents partners from needing inbound access or security tokens to write to Cocoon endpoints.
  * Simpler implementation for partners with pre-existing REST APIs that expose build status.
* **Cons:**
  * High network and resource overhead from frequent, automated polling across numerous partners.
  * Increases latency in reporting status updates back to the Flutter dashboard due to polling intervals.
  * Scale limitations and risk of denial-of-service (DoS) on partner endpoints under heavy load.

### 4.3. Comparison of Options

| Approach Criteria | Primary Design: Webhook Push-Callback | Alternative 1: Event-Driven GCP Pub/Sub | Alternative 2: Automated Polling (Push-Poll) |
| --- | --- | --- | --- |
| **Communication Model** | ✅ Bidirectional HTTP webhooks with manual query backup. | ✅ Asynchronous Event Bus (Pub/Sub). | ✅ HTTP push trigger, automated polling by Cocoon. |
| **Partner Setup Complexity** | ⚠️ **Low to moderate.** Webhooks are easy to consume, but partners must implement retry logic for outbound webhook calls. | ❌ **High.** Requires managing cross-project GCP permissions or GCP service account keys. | ✅ **Low.** Simpler for partners to only set up webhook and status endpoints. |
| **Cloud Vendor Lock-in** | ✅ **Low.** Built on standard REST and HTTP/JWT protocols. | ❌ **High.** Introduces GCP cloud vendor lock-in for third-party partners. | ✅ **Low.** Built on standard REST and HTTP/JWT protocols. |
| **Security & Authentication** | ✅ **Highly secure.** Uses decentralized asymmetric cryptography (Ed25519 JWT) with no central Auth Server. | ⚠️ **Secure.**  Managed via GCP IAM and service accounts. | ✅ **Highly secure.** Uses decentralized asymmetric cryptography (Ed25519 JWT) with no central Auth Server. |
| **Status response validation** | ✅ Can validate payload schema, unknown/duplicated `uid` and notify partner with HTTP response codes. | ⚠️ Can only validate and notify partner about payload schema violation. | ✅ Cannot notify partner of any payload schema or data validation issues. |
| **Latency / Status Reporting** | ✅ **Real-time.** Push-based callback minimizes status reporting latency. | ✅ **Real-time.** Push-based consumption minimizes latency. | ❌ **Higher latency.** Updates are delayed based on Cocoon's polling intervals. |
| **Resilience & Overhead** | ✅ **Highly resilient.** Retries are backed by Pub/Sub; Status query endpoint prevents polling loops. | ✅ **Highly resilient.** Messages are automatically buffered during partner infrastructure outages. | ❌ **High overhead.** Constant automated polling creates network load and risks DoS on partner endpoints. |

## 5. Integration with Existing Features

To support webhook flows, the following must be implemented in Cocoon:

### 5.1. Firestore

#### 5.1.1. partner_config collection

For partner configuration, add a `partner_config` collection with Document ID equal to `task_name`.


### 5.2. Pub/Sub

#### 5.2.1. partner_ci_notification topic

To guarantee that Cocoon can notify each partner CI even during network outages or temporary partner infrastructure outages, once Cocoon reads the post-submit task configuration for a post-submit event, it will send a message to the `partner_ci_notification` topic for every partner integration. A separate instance of Cocoon will receive that message from `partner_ci_notification_sub` and attempt to post it to the partner webhook.

#### 5.2.2. partner_ci_status topic

To guarantee that Cocoon can properly process status updates once the status webhook is called by a partner and the payload is successfully validated, the payload will be sent to the `partner_ci_status` topic and later received by Cocoon from `partner_ci_status_sub` to update the corresponding task status.

## 9. Appendix A. Usage Examples

### 9.1. Communication Example: Cocoon and 3rd Party Partner

#### 9.1.1. Webhook Dispatch Request (Cocoon -> Partner)

When a post-submit commit is processed, Cocoon posts a signed JWT to the partner's webhook URL.
See: [JSON Web Token (JWT) RFC 7519](https://www.rfc-editor.org/info/rfc7519/) for more details about JWT.

##### 9.1.1.1. HTTP POST Request

```http
POST /webhook HTTP/1.1
Host: partner-ci.example.com
Content-Type: application/jwt

<Base64 Encoded JWT Header>.<Base64 Encoded JWT Payload>.<Signature>
```

See: [RFC 7515: JSON Web Signature (JWS)](https://www.rfc-editor.org/info/rfc7515/) for more details about Signature (JWS).

##### 9.1.1.2. Decoded JWT Payload

```json
{
  "iss": "cocoon",
  "aud": "https://partner-ci.com/webhook",
  "iat": 1774962000,
  "exp": 1774962300,
  "data": {
    "uid": "0sAtLhwbmGz2Y0WBDzPL",
    "slug": "flutter/flutter",
    "pr": 12345,
    "sha": "6f0f1c2d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8b"
  }
}
```

Where:

* **iss**: Issuer claim identifying the caller that issued the token (e.g., `cocoon`).
* **aud**: Audience claim specifying the intended recipient URL of the request.
* **iat**: Issued At timestamp (Unix epoch time) indicating when the token was created.
* **exp**: Expiration timestamp (Unix epoch time) after which the token is considered invalid.
* **data**: Object containing custom payload claims and event details:
  * **uid**: The unique correlation identifier to match asynchronous CI execution request to future status response.
  * **slug**: The target repository identifier (e.g., `flutter/flutter`).
  * **pr**: The Pull Request number associated with the event.
  * **sha**: The target git commit SHA hash.

##### 9.1.1.3. HTTP Response

```http
HTTP/1.1 200 OK
Content-Type: application/json

{}
```

#### 9.1.2. Status Callback Request (Partner -> Cocoon)

After executing custom test suites on proprietary hardware, the partner sends the final status back to Cocoon.

##### 9.1.2.1. HTTP POST Request

```http
POST /api/partner/callback HTTP/1.1
Host: cocoon.flutter.dev
Content-Type: application/jwt

<Base64 Encoded JWT Header>.<Base64 Encoded JWT Payload>.<Signature>
```

##### 9.1.2.2. Decoded Payload

```json
{
  "iss": "3p-partner-ci",
  "aud": "https://dashboard.flutter.dev/api/partner/callback",
  "iat": 1774963500,
  "exp": 1774963800,
  "data": {
    "uid": "0sAtLhwbmGz2Y0WBDzPL",
    "status": "failed",
    "message": "Some optional summary if needed",
    "details": [
      {
        "name": "test_1",
        "status": "failed",
        "url": "https://parnter.com/test_1/log"
      },
      {
        "name": "test_2",
        "status": "succeeded",
        "url": "https://parnter-ci.com/test_2/log"
      },
      {
        "name": "test_3",
        "status": "skipped",
        "url": "https://parnter-ci.com/test_3/log"
      },
      {
        "name": "test_4",
        "status": "failed",
        "url": "https://parnter-ci.com/test_4/log"
      },
      {
        "name": "test_5",
        "status": "cancelled",
        "url": "https://parnter-ci.com/test_5/log"
      }
    ]
  }
}
```

Where:

* **iss**: Issuer claim identifying the caller that issued the token (e.g., partner).
* **aud**: Audience claim specifying the intended recipient URL of the request.
* **iat**: Issued At timestamp (Unix epoch time) indicating when the token was created.
* **exp**: Expiration timestamp (Unix epoch time) after which the token is considered invalid.
* **data**: Object containing custom payload claims and event details:
  * **uid**: The unique correlation identifier to match which CI execution request this status response belongs to.
  * **status**:
    * `in_progress` - Task is in progress. Used only for optional `in_progress` status notification. Can not be in terminal status notification.
    * `cancelled` - Task is cancelled by a Partner CI (failure state).
    * `infra_failure` - Infrastructure failure during tests execution (failure state).
    * `failed` - Some or all of the tests are failed (failure state).
    * `succeeded` - All tests passed (success state).
    * `neutral` - Only some flaky tests failed (success state).
    * `skipped` - Some or all tests are skipped (success state).
  * **message**: Optional Markdown formatted message with a summary of CI run. Expected to be present when status is `infra_failure` or `failed`.
  * **details**: Granular test execution details.
    * **name**: Test name.
    * **status**:
    * `in_progress` - Test is in progress. Used only for optional `in_progress` status notification. Can not be in terminal status notification.
      * `cancelled` - Test is cancelled by a Partner CI (failure state).
      * `infra_failure` - Infrastructure failure during test execution (failure state).
      * `failed` - Test failed (failure state).
      * `succeeded` - Test passed (success state).
      * `neutral` - Test failed but considered flaky (success state).
      * `skipped` - Test skipped (success state).
    * **url**: The publicly accessible task execution details or logs URL.

##### 9.1.2.3. HTTP Response

```http
HTTP/1.1 200 OK
Content-Type: application/json

{}
```
