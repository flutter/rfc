# RFC 440.0000: Extensible Enums in Federated Plugins

## Overview

In federated plugins, we often need to expose a set of platform-specific constants (e.g., image formats, barcode types, or sensor configurations). Historically, these have been modeled as standard Dart enums.

However, standard Dart enums represent a closed set of values. When an underlying operating system (Android, iOS, Web, Windows, macOS, Linux) introduces a new feature and we add a new value to the enum to support it, it introduces a breaking change to the platform interface. Any downstream consumer or platform implementation switching over the enum without a default case fails to compile due to Dart's exhaustiveness checks.

To avoid requiring a major version bump each time a plugin adds support for a new native capability, we need a standard pattern across Flutter packages that allows these value sets to grow without breaking backward compatibility.

* **Document Shortlink:** [flutter.dev/go/extensible-enums-plugins](https://flutter.dev/go/extensible-enums-plugins)
* **Audience:** Flutter plugin authors maintaining federated plugins, package contributors, and application developers consuming plugin constants.

---

## Background

Federated plugins separate concerns between the app-facing package (e.g., `camera`), the common platform interface (`camera_platform_interface`), and platform-specific implementations (`camera_android`, `camera_avfoundation`, `camera_windows`, etc.).

Because these packages wrap living, evolving operating systems, the set of supported configurations and capabilities inevitably expands over time.

### Case Study: `camera` and `ImageFormatGroup`

In the `camera` package (see [flutter/packages#11765](https://github.com/flutter/packages/pull/11765)), adding the `rgba8888` format to `ImageFormatGroup` triggered a breaking change because `ImageFormatGroup` was defined as a standard Dart `enum`.

The `camera_platform_interface` must be able to safely add new formats as underlying platform APIs evolve. This scenario recurs across numerous federated plugins that interface with evolving native SDKs (e.g., audio, sensors, biometrics, video player), demonstrating the need for a shared, consistent pattern across the Flutter ecosystem.

### The Two Extensibility Scenarios

Discussions around extensible sets highlight two distinct use cases that an architectural solution must address:

1. **Common Platform Interface Evolution:** The shared platform interface package adds newly supported operating system formats or constants over time across multiple platforms.
2. **Platform Implementation Specialization:** An individual platform implementation (e.g., `camera_android`, `camera_windows`, or a community platform package) needs to introduce platform-specific constants that do not apply to other platforms or are not yet represented in the shared platform interface.

---

## Goals and Non-Goals

### Goals

1. **Non-breaking Additions:** Prevent compilation breaks for downstream consumers and implementations when new values are introduced.
2. **Platform Specialization:** Allow individual platform implementations to define and pass custom values through the platform interface.
3. **Type Safety & Developer Experience:** Retain compile-time type safety, IDE autocompletion, and clear documentation.
4. **Pattern Matching & Control Flow:** Support clean integration with Dart control flow constructs (such as `switch` expressions and statements).
5. **Serialization:** Support straightforward serialization and deserialization (e.g., to and from JSON or platform channels).

### Non-Goals

1. **Deprecating Truly Closed Enums:** Replacing enums that represent naturally closed sets (e.g., values that are fundamentally fixed by domain logic).
2. **Pigeon Serialization Rework:** Replacing Pigeon's internal serialization or fallback mechanisms, which manage their own wire protocol constraints.

---

## Recommendation & Rationale

### Recommendation

The recommended approaches for federated plugins are:

* **Primary Recommendation: Option 7 (Final Class with Properties & Equals/HashCode Override).** Provides the best balance of safety, backward compatibility, and developer ergonomics. It supports standard `switch` statements, simple serialization/deserialization, and allows third parties and platform implementations to instantiate custom constants via constructor or extension.
* **Secondary Recommendation: Option 6 (Class with Properties & Extension Getters).** Suitable when constants must be used as keys in `const` maps or elements in `const` sets, trading `switch` compatibility for `if-else` property matching.
* **Alternative for Dart 3.3+ Packages: Option 2 (Extension Types).** Delivers zero runtime overhead while maintaining an open set of typed constants, suitable for plugins targeting Dart 3.3 or higher.
* **Alternative for Platform Specialization: Option 8 (Base Class as Primitive with Subclasses).** Ideal when platform-specific constants benefit from clear inheritance hierarchy (e.g., `AndroidImageFormatGroup.bgra8888`), making platform provenance explicit at the call site.

### Rationale

For federated plugins where constant domains are dictated by underlying operating systems, values cannot be treated as closed sets.

1. **Open Sets vs. Closed Enums:** Standard Dart enums enforce exhaustiveness. While exhaustiveness is desirable for domain-closed types, it directly conflicts with living API boundaries. Modeling open sets as classes or extension types naturally requires consumers to include a fallback or wildcard branch (`default:` or `_ =>`), preventing downstream build breakage when new constants are added.
2. **The Switch vs. `const` Collection Trade-Off:**
   * Overriding `operator ==` and `hashCode` (as in Option 7 and Option 8) enables direct equality in `switch` statements and pattern matching. However, in Dart, overriding equality precludes instances from being used as keys in compile-time `const` maps or elements in `const` sets.
   * For plugin configuration constants (such as image formats or capture presets), support for `switch` statements is substantially more common and ergonomically valuable than `const` collection indexing.
3. **`knownValues` vs. `values`:**
   * In an extensible or open model, the platform interface cannot know all possible values defined by third-party or platform-specific packages.
   * If a list of constants is provided for iteration, it should be named `knownValues` (rather than `values`) to explicitly communicate that the collection reflects only the core values known at compile time to that package.

## Options Considered

Below are the detailed options evaluated to meet the goals outlined above, using `ImageFormatGroup` as a concrete case study.

### Option 1: Enum with a Private Fallback Value

Continue using standard Dart enums, but introduce a private or dummy value (e.g., `_fallback` or `_unknown`) to the enum definition.

```dart
enum ImageFormatGroup {
  yuv420,
  jpeg,
  nv21,
  rgba8888,
  _fallback, // Forces external users to include a default case
}
```

#### Pros (Option 1)

* Retains standard `enum` syntax and language familiarity.
* **Exhaustiveness workaround:** By intentionally omitting the private dummy value from explicit `case` checks, downstream consumers are forced to provide a `default:` branch, future-proofing their switch statements against new additions.

#### Cons (Option 1)

* Calling `ImageFormatGroup.values` includes `_fallback`, potentially corrupting UI builders or iterators that expect only valid domain values.
* Tooling (e.g., dartdoc, IDE autocomplete) may still surface the private member.
* Semantic mismatch: It subverts Dart's type system intent, as enums are explicitly designed for closed sets.
* Does not allow platform implementations or third parties to define custom constants.

---

### Option 2: Extension Types (Dart 3.3+)

Use Dart 3.3+ `extension type` to wrap an underlying primitive (`String` or `int`), modeling an open set of typed constants with zero runtime overhead.

```dart
extension type const ImageFormatGroup._(String value) {
  static const ImageFormatGroup unknown = ImageFormatGroup._('unknown');
  static const ImageFormatGroup yuv420 = ImageFormatGroup._('yuv420');
  static const ImageFormatGroup rgba8888 = ImageFormatGroup._('rgba8888');
}

String getFormatLabel(ImageFormatGroup format) {
  return switch (format) {
    ImageFormatGroup.unknown => 'Unknown format',
    ImageFormatGroup.yuv420 => 'YUV 420',
    ImageFormatGroup.rgba8888 => 'RGBA 8888',
    _ => 'Default label',
  };
}
```

#### Pros (Option 2)

* **Zero Runtime Overhead:** Compiles down directly to the underlying primitive type at runtime.
* **Non-breaking Additions:** Introducing new `static const` members does not break downstream code.
* **Natural Open Set:** Switch expressions naturally require a fallback (`_ =>`) wildcard.

#### Cons (Option 2)

* No built-in `.values` property: Requires manually maintaining a `static const List<ImageFormatGroup> knownValues`.
* Requires Dart 3.3+, preventing adoption in packages constrained to earlier SDK minimums.
* Less familiar syntax compared to standard classes or enums.

---

### Option 3: Class Types with Static Constants (Dart 3 Modifiers)

Use a standard Dart class with a private constructor and `static const` instances, paired with Dart 3 class modifiers such as `interface class`.

```dart
interface class ImageFormatGroup {
  const ImageFormatGroup._();

  static const ImageFormatGroup unknown = ImageFormatGroup._();
  static const ImageFormatGroup yuv420 = ImageFormatGroup._();
  static const ImageFormatGroup rgba8888 = ImageFormatGroup._();
}
```

#### Pros (Option 3)

* **Non-breaking Additions:** Safe to add new constants over time.
* **Controlled Extensibility:** `interface class` allows third-party implementations to implement the interface (`class CustomFormat implements ImageFormatGroup`).
* Flexible for attaching helper methods and metadata.

#### Cons (Option 3)

* **Equality Pitfall:** If all instances share the same parameterless `const` constructor without unique internal fields, equality checks between instances can fail or collapse unless differentiated.
* Increased boilerplate compared to native enums.
* No built-in collection of values.

---

### Option 4: Raw Primitives (Strings / Integers)

Pass raw primitive values (`String` or `int`) directly across APIs without a wrapper type.

```dart
const String formatUnknown = 'unknown';
const String formatYuv420 = 'yuv420';
const String formatRgba8888 = 'rgba8888';
```

#### Pros (Option 4)

* Absolute simplicity and maximum runtime performance.
* Infinite extensibility: Any caller can pass any string or integer.

#### Cons (Option 4)

* **No Type Safety:** The compiler cannot detect typos (e.g., `'yub420'` instead of `'yuv420'`).
* **Poor Developer Experience:** No IDE autocompletion or method scoping.

---

### Option 5: Open Class Hierarchy (Polymorphism)

Represent each constant as an individual class implementing a common abstract interface or base class.

```dart
abstract class ImageFormatGroup {}

class Yuv420Format implements ImageFormatGroup {}
class Rgba8888Format implements ImageFormatGroup {}
```

#### Pros (Option 5)

* **Non-breaking Additions:** An open (unsealed) class hierarchy requires switch statements to include a fallback case.
* **Payload Support:** Formats can encapsulate complex platform-specific metadata or parameters.

#### Cons (Option 5)

* Significant boilerplate and over-engineering for simple domain constants.
* Unwieldy syntax for common constant comparisons.

---

### Option 6: Class with Properties and Extension Getters

Use a `base class` with a public const constructor, internal property, and boolean getters. Platform packages or external consumers can add custom values using Dart extension methods.

```dart
base class ImageFormatGroup {
  const ImageFormatGroup(this.value);

  final String value;

  static const ImageFormatGroup unknown = ImageFormatGroup('unknown');
  static const ImageFormatGroup yuv420 = ImageFormatGroup('yuv420');
  static const ImageFormatGroup rgba8888 = ImageFormatGroup('rgba8888');

  bool get isUnknown => value == 'unknown';
  bool get isYuv420 => value == 'yuv420';
  bool get isRgba8888 => value == 'rgba8888';
}

// In camera_android or third-party package:
extension CustomImageFormatGroup on ImageFormatGroup {
  static const ImageFormatGroup bgra8888 = ImageFormatGroup('bgra8888');
  bool get isBgra8888 => value == 'bgra8888';
}

String getFormatLabel(ImageFormatGroup format) {
  if (format.isUnknown) {
    return 'Unknown format';
  } else if (format.isYuv420) {
    return 'YUV 420';
  } else if (format.isRgba8888) {
    return 'RGBA 8888';
  } else if (format.isBgra8888) {
    return 'BGRA 8888';
  } else {
    return 'Default label';
  }
}
```

#### Pros (Option 6)

* Safe, non-breaking additions over time.
* Extensible outside the defining package via extension methods.
* Because equality and hash code are not overridden, `const` instances can be used as keys in `const` maps and elements in `const` sets.
* Intuitive and beginner-friendly, avoiding complex language mechanisms.

#### Cons (Option 6)

* Does not support `switch` expressions/statements cleanly; requires `if-else` branching on boolean getters.
* Requires manual boilerplate for getters.

---

### Option 7: Final Class with Properties and Equals/HashCode Override

Model the extensible constant as a `final class` containing an underlying identifier, a public `fromString` constructor, and explicit `operator ==` and `hashCode` overrides.

> [!NOTE]
> This pattern is modeled after the approach adopted in [`dart-lang/native#3413`](https://github.com/dart-lang/native/pull/3413) for target operating systems (`OS`) and architectures (`Architecture`). Here, it is adapted to the `ImageFormatGroup` case study.

```dart
final class ImageFormatGroup {
  final String name;

  const ImageFormatGroup._(this.name);
  const ImageFormatGroup.fromString(this.name);

  static const ImageFormatGroup unknown = ImageFormatGroup._('unknown');
  static const ImageFormatGroup yuv420 = ImageFormatGroup._('yuv420');
  static const ImageFormatGroup jpeg = ImageFormatGroup._('jpeg');
  static const ImageFormatGroup nv21 = ImageFormatGroup._('nv21');
  static const ImageFormatGroup rgba8888 = ImageFormatGroup._('rgba8888');

  static const List<ImageFormatGroup> knownValues = <ImageFormatGroup>[
    unknown,
    yuv420,
    jpeg,
    nv21,
    rgba8888,
  ];

  @override
  bool operator ==(Object other) =>
      identical(this, other) ||
      other is ImageFormatGroup && other.name == name;

  @override
  int get hashCode => name.hashCode;

  @override
  String toString() => 'ImageFormatGroup.$name';
}

// Third-party or platform-specific extension (e.g. in camera_windows):
extension CustomImageFormatGroup on ImageFormatGroup {
  static final ImageFormatGroup bgra8888 =
      ImageFormatGroup.fromString('bgra8888');
}

// Switch statements and expressions work directly:
void handleFormat(ImageFormatGroup format) {
  switch (format) {
    case ImageFormatGroup.yuv420:
      print('Processing YUV 420');
    case ImageFormatGroup.rgba8888:
      print('Processing RGBA 8888');
    default:
      print('Other format: ${format.name}');
  }
}
```

#### Pros (Option 7)

* **Switch Compatibility:** Supports standard `switch` statements and expressions directly via value equality.
* **Non-breaking Additions:** New constants can be added to the class or via extensions without breaking existing code.
* **Extensible by Third Parties:** Platform packages can define new values using `ImageFormatGroup.fromString(...)`.
* **Serialization Ready:** Trivially serializes to and deserializes from primitive strings (`format.name` and `ImageFormatGroup.fromString(...)`).
* **Idiomatic Dart:** Standard class semantics familiar to all Dart developers.

#### Cons (Option 7)

* Cannot be used as keys in compile-time `const` maps or elements in compile-time `const` sets due to overriding `operator ==` and `hashCode`.
* Runtime overhead of small object allocations (mitigated when `const` constructors are utilized).

---

### Option 8: Base Class as Primitive with Subclasses

Use a `base class` with protected constructor and value equality, allowing individual platform packages to define their own platform-specific subclasses.

```dart
base class ImageFormatGroup {
  final String value;

  @protected
  const ImageFormatGroup(this.value);

  @override
  bool operator ==(Object other) =>
      identical(this, other) ||
      other is ImageFormatGroup && value == other.value;

  @override
  int get hashCode => value.hashCode;

  static const ImageFormatGroup unknown = ImageFormatGroup('unknown');
  static const ImageFormatGroup yuv420 = ImageFormatGroup('yuv420');
  static const ImageFormatGroup rgba8888 = ImageFormatGroup('rgba8888');
}

// In camera_android:
final class AndroidImageFormatGroup extends ImageFormatGroup {
  const AndroidImageFormatGroup(super.value);

  static const AndroidImageFormatGroup bgra8888 =
      AndroidImageFormatGroup('bgra8888');
}

// Optional platform extension to expose base-type getters:
extension AndroidImageFormatExtension on ImageFormatGroup {
  bool get isBgra8888 => this == AndroidImageFormatGroup.bgra8888;
}
```

#### Pros (Option 8)

* **Explicit Platform Provenance:** Subclasses make it immediately obvious which platform defines a specific constant (e.g., `AndroidImageFormatGroup.bgra8888`), preventing ambiguity in multi-platform codebases.
* Enables runtime type checks (e.g., `if (format is AndroidImageFormatGroup)`).
* Supports `switch` statements via value equality.

#### Cons (Option 8)

* Downstream code typed to the base class cannot access subclass members without either casting, equality comparison (`format == AndroidImageFormatGroup.bgra8888`), or helper extension getters.
* Cannot be used in `const` maps/sets due to `==` override.
