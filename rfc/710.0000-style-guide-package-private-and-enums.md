# RFC 710.0000: Style guide changes for package private and enums

## Overview

This document proposes updating the [Flutter repository style guide](https://github.com/flutter/flutter/blob/main/docs/contributing/Style-guide-for-Flutter-repo.md) and [Flutter breaking change policy](https://github.com/flutter/flutter/blob/main/docs/contributing/Tree-hygiene.md#handling-breaking-changes) to adopt `@internal` for package-private APIs and establish conventions for public enums.

Declarations marked `@internal` are outside the public API contract; modifying or removing them is not a breaking change. For public APIs, a standard `enum` is used when consumers must handle all values exhaustively (making new values a breaking change), and a class with `static const` fields is used when consumers need a fallback (making new values non-breaking).

## Context

### Package-private APIs

The style guide discourages package-private APIs beyond library-private (`_`) declarations and requires every file in `lib/src/<layer>/` to be exported by `lib/<layer>.dart`. In practice, when file-scoped `_` privacy is too narrow, the framework already omits `_`-prefixed files in `lib/src/` from barrel exports (such as `lib/src/widgets/_window.dart` and `lib/src/foundation/_features.dart`).

Relying on filename conventions alone risks accidental leaks. Because `lib/src/` files are re-exported by default, moving code or sharing a non-private class within a layer can inadvertently expose it to external consumers, making future edits breaking changes. Marking these declarations `@internal` triggers an `invalid_internal_annotation` analyzer warning if exported, prompting contributors to move them to an unexported `_` file or hide them in the barrel export.

### Enums

Inside the Flutter codebase, requiring exhaustive `switch` statements and expressions over `enum` values (without `default` branches) is intentional and remains unchanged. However, the style guide lacks guidelines for designing enum-like types in public APIs, and the breaking change policy does not explicitly classify adding a value to a public `enum` as a breaking change.

Because external callers also switch exhaustively over public `enum` types, adding a new value breaks downstream code. Without criteria for choosing between a standard `enum` and a class with `static const` fields, public APIs in the framework are inconsistent:

* `TargetPlatform` and `AppLifecycleState` are `enum` declarations even though consumers typically handle only specific values with a fallback. Adding new values breaks callers.
* `TextInputType` and `LogicalKeyboardKey` use classes with `static const` fields to allow non-breaking additions, but the style guide does not document when to use this pattern instead of an `enum`.

## Proposal

### Breaking change policy exemption

Modifying, renaming, or removing any declaration annotated with `@internal` is not a breaking change and requires no deprecation period or announcement.

### Package-private APIs (`@internal`)

Use `@internal` from `package:meta` when an implementation detail is shared across files within the same layer (`lib/src/<layer>/`) or accessed by framework unit tests in `packages/flutter/test/`.

#### Placement rules

* `@internal` may be applied to top-level declarations and to `static` members or constructors of public classes inside `lib/src/`.
* In any file in `lib/src/` not exported by a barrel file, all public top-level declarations must be annotated with `@internal`.
* `@internal` must not be applied to an instance member of a public class unless both:
  * The enclosing class has the `base`, `final`, or `sealed` modifier so external packages cannot `implement` it.
  * The instance member is annotated with `@nonVirtual` so subclasses cannot override it.

#### Barrel exports and file naming

* Any file in `lib/src/<layer>/` not exported by `lib/<layer>.dart` must have a `_` filename prefix (such as `lib/src/widgets/_window.dart`), and have all public top-level declarations annotated with `@internal`.
* When an `@internal` top-level declaration shares a file with public declarations, `lib/<layer>.dart` and any intra-`src/` re-export must exclude it with `hide` (such as `export 'src/widgets/foo.dart' hide InternalBar;`).
* Cross-layer imports in `lib/src/` must continue importing top-level barrel files (`package:flutter/<layer>.dart`) rather than another layer's `lib/src/` files.

### Enums

#### Non-public enums

Library-private (`_`) and `@internal` enums must use a standard `enum` declaration so framework `switch` statements and expressions are exhaustively checked.

#### Public APIs

Choose between a standard `enum` and an enum-like class based on whether consumers must handle every value exhaustively, rather than whether new values might be added later:

##### Standard `enum` (exhaustive)

Use a standard `enum` when consumers are expected to handle every case without a `default` or `_` branch (such as `Axis`, `AxisDirection`, `VerticalDirection`, and `GrowthDirection`).

* Provides compile-time exhaustiveness checking.
* Adding a value to a public `enum` is a breaking change, forcing consumers to handle the new case.

##### Enum-like class with `static const` values (non-exhaustive)

Use a `final` class with a private `const` constructor and `static const` fields when consumers handle a subset of values with a `default` or `_` fallback (such as `TextInputType` and `LogicalKeyboardKey`; existing enums like `TargetPlatform` and `AppLifecycleState` also fit this category).

* Adding a `static const` field is not a breaking change.
* Does not provide compile-time exhaustiveness checking.

## Open questions

### Removing discouragement of `@visibleForTesting`

The style guide section "Avoid using `@visibleForTesting`" advises against `@visibleForTesting` on public declarations, preferring APIs testable through their public interfaces, though contributors still use it when necessary. Should the style guide remove its discouragement of `@visibleForTesting` or keep the current stance?

### Adopting `@experimental` for cutting-edge development

New public APIs immediately fall under the breaking change policy, requiring an RFC, deprecation cycle, and migration guide to modify or remove. Should Flutter adopt [`@experimental`](https://pub.dev/documentation/meta/latest/meta/experimental-constant.html) from `package:meta` to exempt cutting-edge APIs from the breaking change policy?

### Handling feature flag files and the cross-layer import rule

`lib/src/foundation/_features.dart` defines `@internal` feature flags consumed by higher layers (for example, `lib/src/widgets/binding.dart` imports `../foundation/_features.dart`). Because `@internal` symbols cannot be exported by `lib/foundation.dart`. What should be done about feature flags?
