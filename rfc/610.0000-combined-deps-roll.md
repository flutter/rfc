# RFC 610.0000: Combined DEPS Roll

## Summary

Automated `DEPS` rolls across six projects currently generate ~41% of all open PRs in `flutter/flutter` (27% of merged commits), but achieve only a 32.3% merge rate. Since every `DEPS` change triggers the entire presubmit test suite, this low success rate causes substantial CI resource waste.

This doc proposes that the Flutter Infra team build and own a new DEPS autoroller, replacing the Skia autoroller for these six dependencies. The new roller employs three strategies: better deflake, combined rolls, and throttling roll frequency. Together, these optimizations will cut autoroll PR volume by about 85%, or total PR volume by about 35% across the Flutter repository.

## Scope

This document seeks agreement on **what** we propose to build and **why**:

* Building a new, Flutter-owned DEPS autoroller that replaces the existing Skia autoroller configurations for the six dependencies listed in [Appendix A](#appendix-a---configured-rollers-on-skia-autoroller).
* The three strategies the new roller will employ, and the expected savings.
* The rollout order, at a high level.

The following is explicitly **out of scope** for this document:

* **Detailed design.** The architecture, state machine, data model, configuration schema, hosting, and APIs of the new roller will be covered in a separate design document once this proposal is accepted. The [High-level design](#high-level-design) section below describes the approach only to the extent needed to evaluate the proposal.

## Background

The Skia autoroller rolls 6 different projects into the Flutter repo that touch the `DEPS` file. The frequencies of these rolls are listed in [Appendix A](#appendix-a---configured-rollers-on-skia-autoroller).

They make up about 27% of all merged commits (see [Appendix D](#appendix-d---commit-categorization-1000-commits)), and about 40% of all PRs open (see [Appendix B](#appendix-b---autoroller-pr-stats)). All PRs updating the `DEPS` file have to run all builders in presubmit as `DEPS` file changes are considered engine changes.

The Skia autoroller never deflakes any failing tests. If a test fails due to a flake, it abandons the roll ([example](https://github.com/flutter/flutter/pull/191772)). As a result, only 32.3% of all PRs opened by the Skia autoroller are actually merged, which causes a lot of waste in CI resources.

## Proposal

We propose building a new, Flutter-owned autoroller for these six dependencies to replace the existing Skia autoroller configurations. The new roller will implement the three strategies below.

Individually, better deflaking could potentially be implemented within Cocoon, and throttling is already supported by the Skia autoroller. Combined rolls, however, cannot be implemented in any existing system, and owning the roller gives the team observability and control over the rolling infrastructure that it lacks today. We therefore propose implementing all three strategies in the new roller rather than piecemeal across Cocoon and the Skia autoroller.

### Better deflake

Deflake the tests at least once before abandoning the roll PR—re-running only the failed LUCI check(s) in-place on the same PR, rather than abandoning the PR and opening a new one that re-runs all 100+ presubmit builders from scratch. Based on the 32.3% merge rate (67.7% failure rate), assuming that 80% of the failed PRs are due to flakes (~54.2% of all roll PRs failing due to flakes vs. ~13.5% due to actual breakages), this could theoretically save ~54% of runs (and an even larger share of individual builder executions, since only failed checks are retried).

Cons: Slower recovery from true failure. If there are actual failures, we spend time waiting for a deflake instead of failing fast. However, because test flakes are much higher than actual failures for rolls (~80% of failures are flakes vs. ~20% actual breakages), this con is relatively small in practice.

This can potentially be implemented within Cocoon.

### Combined rolls

Instead of having each dependency rolling into Flutter independently, the roller could merge the rolls into a single PR if multiple projects are updated. This could save ~35% (~29% from the previous step).

When a combined roll fails, the autoroller should split the PR and roll the dependencies independently. Only the dependencies that are healthy (i.e. had a successful roll) should be combined with other dependencies.

Cons: Slower and more complicated failure detection and recovery.

This cannot be trivially implemented in any existing systems, so the team would have to invest in a new autoroller. The Flutter Infra team does not own the current `skia-autoroller`, meaning we currently have no insight into why the autorollers go down or fail sometimes. Writing an open-source autoroller owned by the team would provide better observability and go towards maintainability of infrastructure through reduced dependencies.

### Throttle rolls

The roller currently opens about 4 roll PRs per day for Dart, merging 2 per day, and about 7 roll PRs per day for Skia, merging 3 per day. If PRs are throttled to 2 per day, this could save ~30% (~55% from the previous step).

The existing Skia autoroller already supports this via `roll_cooldown`:

* Dart -> Flutter roll is [configured](https://skia.googlesource.com/skia-autoroll-internal-config/+/3a59d4c854fec49ce97fdd06cecd3e07de8e3d5c/skia-infra-public/dart-sdk-flutter.cfg#15) to have `roll_cooldown: 3h`.
* Skia -> Flutter roll is [not configured](https://skia.googlesource.com/skia-autoroll-internal-config/+/main/skia-infra-public/skia-flutter.cfg) with `roll_cooldown`.

Cons: Longer delay to get changes into the Flutter repo.

### Total potential savings

If we implement all three strategies, the theoretical total savings would be about an 85% reduction on the number of autoroll PRs, or about a 35% reduction on the number of all PRs.

For reference, deflaking and combined rolls alone account for about a 67% reduction on the number of autoroll PRs, or about a 27% reduction on the number of all PRs; the remainder comes from throttling, so the realized savings depend on the configured roll frequency.

See [Appendix C](#appendix-c---saving-calculation) for how we got the numbers.

## Key features

In addition to the three strategies above, the new roller should provide the following (its detailed design is deferred to the separate design document):

* **Per-dependency commit log in roll PRs.** PRs generated by the Skia autoroller already include the revision range and list of upstream commits (with authors and links) for the rolled dependency. The new roller must preserve this behavior—listing the revision range and commit log for each dependency included in a combined or individual roll PR—so it remains straightforward to identify the culprit dependency and revert only that dependency, as described in the [FAQ](#how-do-we-handle-reverts).

## High-level design

> [!IMPORTANT]
> This section describes the intended approach only at a high level, to the extent needed to evaluate the proposal and its savings estimates. The detailed design (architecture, state machine, data model, configuration schema, hosting, and APIs) is **out of scope** for this RFC and will be covered in a separate design document.

Implement a new autoroller to roll these 6 dependencies. The autoroller will roughly follow the design of the Flutter -> g3 autoroller, using the level-triggered state machine pattern where the source of truth is in external systems.

At any given time, there can only be one ongoing combined roll, and one ongoing roll for each dependency. If a dependency is healthy, it should be in the combined roll. Otherwise it should be rolled independently.

The autoroller will be implemented in a reconciliation loop pattern to ensure resilience to failure and idempotency.

When the autoroller runs, it will check if there is an ongoing roll. If an ongoing roll doesn't exist, and time since the last successful roll is > X hours, then start a new roll.

If there is an ongoing roll, check the test status. If any of the tests failed, retry the failed LUCI check(s) in-place on the same PR up to two times to deflake, and if the tests still fail after two retries, declare the roll failed.

When the tests pass, the roller will add the `autosubmit` tag and let the other bot handle merging the PR.

The roller should also be controllable with a config that allows us to pause the roll for a certain dependency, temporarily disable combined rolls, configure the roll frequency, etc.

In case of emergency, the team could always fall back to manual rolls.

## Rollout plan

We will start with combining Dart and Fuchsia Linux SDK, the 3 others, and then Skia. As each dependency is migrated, the corresponding Skia autoroller configuration will be disabled so that only one roller is active per dependency.

## FAQ

### Why build a new roller instead of improving the existing one?

We don't control the Skia autoroller, which is used in more projects. Updating the Skia autoroller requires more effort. Furthermore, because the Flutter Infra team does not own `skia-autoroller`, we have no insight into why the autorollers go down or fail sometimes. Writing an open-source autoroller gives us better observability and reduces external infrastructure dependencies.

Also we already have experience developing and maintaining our own roller, the Flutter -> g3 autoroller.

### How do we handle reverts?

In most cases we will revert a single dependency if we need to, instead of the whole commit. The dependencies are mostly unrelated to each other so it will be obvious, in most cases, which dependency is causing a breakage.

Also the update for each dependency is only a single line in the `DEPS` file, therefore there are no concerns about conflicts.

The dependencies are mostly unrelated and the concern about them affecting each other is minimal.

## Appendix C - Saving calculation

Based on the numbers in [Appendix B](#appendix-b---autoroller-pr-stats).

### Deflake savings

* PRs opened by autoroller = 910
* PRs merged by autoroller = 294
* PRs failed percentage = 67.69%
* Assuming 80% flaky, PRs failed due to flake = 54.15%
* Total number of PRs = 417
* Savings ~54%

### Combined roll savings

Total number of rolls would be equal to the number of the most frequently rolled project, i.e. Skia roll.

From the previous step, assuming 80% flaky:

* Number of Skia PRs = 229
* Assuming 10% of the rolls failed and need to be retried individually, with 3 projects (somewhat frequently rolled projects), 68 rolls retried.
* Total number of PRs = 297
* Savings ~29% from the previous step, or 67% overall so far.

### Throttle savings

* Number of rolls became 120. Plus 10% retry with 3 projects, total number of rolls = 132.
* Savings ~55% from the previous step, or 85% overall.

### Savings over all PRs

* Autoroll PRs are 40.7% of all open PRs.
* 67% savings in autoroll PRs = 27% savings overall.
* 85% savings in autoroll PRs = 35% savings overall.
