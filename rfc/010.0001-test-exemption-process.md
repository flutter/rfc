# RFC 010.0001: Test Exemption Process

## Overview

If a PR needs an exemption from our testing guidelines, those exemptions are currently granted by a `@test-exemption-reviewer` role on Discord. Originally, this responsibility was managed by `@Hixie`. Upon his departure from the team, the role was taken over by `@stuartmorgan-g`, who is also leaving. With his departure, we are looking at reworking this system to be more sustainable and distribute this responsibility more broadly so as to avoid a single point of failure.

## Possible solutions

A description of the adopted solution can be found in the [Decision](#decision) section. Below is some discussion of the solutions that were considered.

### Test Exemptions Handled by Tech Lead

One solution is to assign this responsibility to the tech lead for the given area the PR touches. When a PR is being reviewed, reviewers should generally push back on changes that have no tests, but if the reviewer agrees the change warrants an exception to our testing guidelines they can ask the tech lead for that area to approve the test exemption. This solution has a few benefits:

* Naturally distributes the workload of granting test exemptions to multiple people.
* The person granting test exemptions has the domain expertise to understand the ramifications of granting an exemption.
* We can eliminate the `@test-exemption-reviewer` role and associated maintenance. One of the main responsibilities for the `@test-exemption-reviewer` role is often handling "cold" test exemption requests from external contributors who are unfamiliar with our process. Since approved code reviewers are members of `flutter-hackers`, they generally understand this process and can prevent the need for someone to come to Discord to ask for an exemption when it is not needed.

There are some drawbacks to this process, however:

* If a PR touches multiple areas or some area of the code which has ambiguous ownership, it may be unclear which tech lead should be asked to grant a test exemption.
* Often, the originator of the PR or the reviewer may be the tech lead themselves. In that case, it can become difficult to make an objective decision about whether or not an exemption is warranted. Having an explicit "test exemption reviewer" role separate from the originator or the reviewer of the role helps ensure that there is always someone with a fresh perspective available to evaluate requests for test exemptions.
  * To mitigate this, one possibility is to always ask for a second opinion from another tech lead in such a case. That way, the originator or reviewer is not the same person as the one granting the test exemption.

A remaining question for this option is whether trusted external contributors should have the authority to grant test exemptions for PRs that they review. There are some examples of the Flutter codebase which are now owned by non-Googlers. For example, Canonical owns the desktop embedder, and already has some elevated privileges in landing PRs to that area. Should we designate an external "tech lead" which can approve test exemptions for PRs to that area of the codebase?

### Having a `@test-exemption-reviewer` Rotation

Another possibility is to stick closer to the current process, but to institute a rotation of `@test-exemption-reviewer` such that there is always someone available to handle test exemption requests. The benefits to this solution include:

* This is the closest thing to our current process, and requires the least amount of adjustment and education around it for existing contributors to the project.
* Having a rotation ensures that the person on rotation is indeed available for granting exemptions, and not out of the office or on vacation.

There are some drawbacks to this solution, however:

* Having a rotation and handoff for this role each week does have some overhead associated with it.
* This solution doesn't allow us to eliminate the `@test-exemption-reviewer` role, and we still need someone to handle "cold" test exemptions requests from external contributors.

### Some hybrid solution to the above

We could consider some combination of the above, where tech leads are the default reviewers for test exemptions, but we retain the `@test-exemption-reviewer` role for situations where the tech lead is not available (or is an originator or reviewer of the PR), the ownership is ambiguous, or for "cold" test exemption requests from external contributors.

## Infra/Tooling changes

Whichever solution we choose, now is probably a good time to update our tooling to better support this process. As of right now, we have a bot which looks at the PR and determines whether or not it has tests, and posts a comment to the PR notifying this and outlining our current test exemption process. However, this doesn't actually create a hard barrier to enforcing this process. The PR can still be merged, even if the comment is dropped there. A few changes to our infra tooling would tighten up our enforcement of this policy and clarify things:

* Change the comment posted in the PR to accurately match the process according to the solution we choose.
* The bot should add a `missing-tests` label if a PR is missing tests, and keep the state of that label up-to-date with each push. That is to say, the label should be removed if a subsequent push adds tests, or if the change no longer touches code which requires tests.
* Whoever is responsible for granting test exemptions is responsible for adding a `test-exempt` label. This will allow the test exemption process to be more auditable, since the GitHub history will reflect who added the label.
* The autosubmit bot should prevent a PR from being merged if it has a `missing-tests` label but not a `test-exempt` label.
* We will need to update our documentation in `flutter/flutter` to reflect whichever new solution we choose.

## Decision

After a vote among the Flutter Tech leads, we landed on the following solution moving forward:

* Flutter Tech Leads will be responsible for granting test exemptions for PRs which touch their area of the codebase.
* Reviewers are responsible for escalating test exemptions to the tech lead for the given area.
* Infra tooling will be updated to support this process, adding a `missing-tests` label to PRs which are missing tests, and a `test-exempt` label to PRs which have been granted a test exemption. The autosubmit bot should prevent a PR from being merged if it has a `missing-tests` label but not a `test-exempt` label.
* Only tech leads are permitted to add the `test-exempt` label. However, this is not strictly enforced, as anyone with write access can add this label to the repo, so this is sort of an "honor system" policy. We will clearly document the policy and revisit this decision if we find this loophole is being abused.
* For PRs that are originated by tech leads or reviewed by tech leads, the policy will be that the tech lead is responsible for ensuring that a second tech lead reviews the PR and approves the test exemption.
* For now, the list of tech leads that can allow test-exemptions is limited to Googlers. This can be revisited if there is a strong need to change this policy.
* The documentatioun in `flutter/flutter` will be updated to reflect the new process.
* The `@test-exemption-reviewer` role will expanded to include all tech leads, and a Discord channel for internal discussion among test exemption reviewers will be added.
